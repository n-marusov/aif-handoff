# Функциональные требования — AIF Handoff: система автономного управления задачами

В этой директории хранятся формализованные функциональные требования (FR) к системе **AIF Handoff — автономное управление задачами** (`aif-handoff`): модульному монолиту на Turborepo, реализующему hand-off-конвейер с AI-субагентами через подключаемые runtime-адаптеры. Каталог содержит **только функциональные требования**; нефункциональные (NFR) ведутся вне этой директории, в [nonfun-req/](../nonfun-req/README.md), а бизнес-правила (`BR-*`) — в [business-rules/](../business-rules/README.md).

FR описывают поведение AIF Handoff на стороне ядра (api + agent + coordinator). Внешние AI-провайдеры (Claude Agent SDK, Codex, OpenRouter), VCS-платформы (GitHub, GitLab) и веб-браузер — внешние системы; требования к их внутренним функциям вне контура.

Методологическая основа: Software Requirements Engineering (Wiegers & Beatty, 3rd ed.) — трёхуровневая модель требований (business → user → functional/nonfunctional) и цикл разработки требований (Elicitation → Analysis → Specification → Validation).

## Иерархия требований

Требования организованы по трём уровням (W&B: Business / User / Functional requirements). Структура `docs/` в этом репозитории:

```
docs/
├── vision.md — бизнес-требования (Business): SMART-цели G1–G7, проблемы P1–P8, функции HF1–HF12, MVP, roadmap
├── use-cases/ — прецеденты использования (User): детализация пользовательских сценариев (UC) → UC-*
├── fun-req/   — функциональные требования (FR): детализация UC → REQ-FR-*
├── nonfun-req/ — нефункциональные требования (NFR): границы качества поверх FR → REQ-NFR-*
├── business-rules/ — бизнес-правила (BR): политики и ограничения → BR-*
├── adr/ — архитектурные решения (ADR)
├── domain/ — DDD-модель: контексты, агрегаты, события, словарь данных
```

Связи между артефактами:

- **UC — детализация пользовательских историй**: UC выводятся из US (HF{1..12}.{1..N} из `vision.md` §2.2) и трассируются на них (поле «Источник требований»).
- **FR детализируют UC**: каждый FR выводится из одного или нескольких UC и трассируется на них (поле «Источник»); к US FR восходят через UC.
- **NFR задают границы качества** поверх FR (производительность, доступность, безопасность) и не дублируют функциональность.
- **BR — отдельный актив** enterprise-уровня: политики и ограничения, разделяемые всеми артефактами.

## FR в жизненном цикле требований

FR — артефакт стадии **Specification**: UC (User requirements) детализируются в отдельные FR. Стадии цикла W&B применяются к FR так:

| Стадия            | Что делаем с FR                                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Elicitation**   | Источники: UC (`use-cases/`), функции HF1–HF12 и проблемы P1–P8 из `vision.md`, бизнес-правила `BR-*` (`business-rules/`); для `as is`-UC — фактическое поведение системы |
| **Analysis**      | Декомпозиция UC до атомарных FR; отделение от NFR и бизнес-правил (`BR-*`)                                                                                                |
| **Specification** | Оформление FR по шаблону: ID, приоритет, ключевая функция, источник, описание, критерии приёмки                                                                           |
| **Validation**    | Ревью (критерии качества и чек-лист дефектов ниже), проверка критериев приёмки, написание тестов; автоматическая проверка — гейты G1-\*                                   |

## Формат идентификатора FR

```
REQ-FR-<L1>.<L2>.<action>
```

Где:

| Часть      | Описание                                                                                                  | Допустимые значения                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L1**     | Домен — соответствует доменам UC (`use-cases/README.md`, колонка L1) и функциям HF1–HF12 `vision.md` §2.2 | `pipeline` · `dashboard` · `runtime` · `vcs-auto` · `accounting` · `handoff` · `chat` · `auth` · `audit` · `integration` · `warmup`                                                                                                                                                                                                                                                                                                                                                                                                            |
| **L2**     | Поддомен — соответствует поддоменам UC (там же, колонка L2) и подфункциям HF{1..12}.{1..N}                | `stage` · `plan` · `implementation` · `verification` · `completion` · `manual-override` · `gate` · `sidecar` · `review-loop` · `board` · `gate-status` · `detail` · `realtime` · `search` · `profile` · `override` · `external-adapter` · `isolation` · `commit` · `mr` · `plan-review` · `tracking` · `limits` · `blocking` · `transfer` · `escalation` · `history` · `diagnostics` · `project-context` · `task-context` · `registration` · `roles` · `logging` · `heartbeat` · `errors` · `issues` · `pr-mr` · `ci-status` · `preheat` и др. |
| **action** | Семантическая метка в kebab-case, отражающая конкретное действие/поведение                                | Свободная семантическая метка                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

> **Домены — допустимые значения** из UC L1. Домены FR совпадают с доменами UC, что обеспечивает прямую трассировку FR → UC. Если новый UC вводит домен/поддомен вне списка, список доменов UC в `use-cases/README.md` расширяется первым (единый источник L1/L2 для UC и FR).

### Правила именования

1. Только **kebab-case**, без цифр и индексов.
2. **L1** — строго из списка доменов. Домены, не соответствующие HF1–HF12 (например, `infrastructure`, `deployment`), не применяются.
3. **L2** — строго из списка поддоменов (допустимые значения в `use-cases/README.md`, колонка L2).
4. **action** — свободная семантическая метка, отражающая конкретное функциональное поведение.

### Примеры

| REQ-ID (проект)                                   | Источник (UC)                                                                                          | Описание                                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `REQ-FR-pipeline.stage.auto-advance-after-gate`   | [UC-pipeline.stage.auto-advance-task](../use-cases/UC-pipeline.stage.auto-advance-task.md)             | Автоматический переход задачи на следующую стадию после успешного прохождения формального гейта |
| `REQ-FR-pipeline.plan.generate-plan-from-context` | [UC-pipeline.plan.generate-change-plan](../use-cases/UC-pipeline.plan.generate-change-plan.md)         | Генерация плана изменения на основе контекста задачи (Issue, требования, код)                   |
| `REQ-FR-dashboard.board.render-kanban-columns`    | [UC-dashboard.board.view-kanban-columns](../use-cases/UC-dashboard.board.view-kanban-columns.md)       | Отображение задач в виде Kanban-колонок, сгруппированных по стадиям конвейера                   |
| `REQ-FR-handoff.transfer.change-executor`         | [UC-handoff.transfer.ownership-to-executor](../use-cases/UC-handoff.transfer.ownership-to-executor.md) | Смена исполнителя задачи с сохранением полной истории владения                                  |
| `REQ-FR-audit.logging.record-state-transition`    | [UC-audit.logging.audit-state-transition](../use-cases/UC-audit.logging.audit-state-transition.md)     | Иммутабельная запись каждого перехода задачи между стадиями с указанием актора и времени        |

## Правила оформления

1. **Один файл — одно атомарное требование.**
2. **Имя файла**: `REQ-FR-<L1>.<L2>.<action>.md`.
3. **Язык**: русский. Технические термины — на английском.
4. **Обязательные поля**:
   - **Приоритет:** `P0` / `P1` / `P2`
   - **Ключевая функция:** ссылка на функцию/подфункцию HF1–HF12 из `vision.md` §2.2 (например, HF1.2, HF5.3)
   - **Источник:** ссылка на породивший UC, функцию/подфункцию HF1–HF12 (§2.2), проблему P1–P8 (§1.1) и, при наличии, бизнес-правило `BR-*` из `business-rules/`
   - **Описание:** суть требования
   - **Критерии приёмки:** измеримые условия выполнения
5. **Рекомендуемые поля** (атрибуты требований, W&B Chapter 27):
   - **Статус:** `proposed` → `approved` → `implemented` → `verified` → `deleted` (отслеживание статуса)
   - **Класс UC:** `as is` / `to be` — наследуется от породившего UC (см. `use-cases/README.md`, «Классификация UC»): FR из `to be`-UC описывают целевую capability и помечаются фазой roadmap (`vision.md` §2.5)
   - **Связанные требования:** ссылки на родственные FR/NFR
   - **Бизнес-правила:** ссылки на `BR-*` из [business-rules/](../business-rules/README.md), если FR ограничен правилом
   - **Канал:** `GUI` / `API` (REST) / `Agent` (coordinator) / `Schedule` / `Mixed` — наследуется от UC
6. **TBD-флаг**: пробелы в требовании помечаются `TBD` и фиксируются в реестре [open-questions.md](../open-questions.md) — требование не считается готовым, пока TBD не закрыт.
7. **Трассируемость**: каждый FR ссылается на породивший его UC в поле «Источник» (FR → UC → US → vision.md). Цепочка трассируемости: `Vision (HF1–HF12) → US → UC → FR → ADR → COMP → TEST`. Связь US → UC фиксируется в UC (поле «Источник требований»); US не трассируются на FR напрямую — через UC.

## Приоритеты

Приоритет определяет порядок реализации (W&B: prioritization по ценности, стоимости и риску) и **согласуется с приоритетом породившего UC**:

- **P0** — критическое: без него MVP невозможен (hand-off-конвейер с автоматическим прохождением стадий — HF1, формальные гейты — HF5, атомарный MR — HF4.3, аутентификация — HF9.1)
- **P1** — важное: ключевая пользовательская потребность (дашборд с real-time обновлениями — HF2, handoff и эскалация — HF7, чат с AI-ассистентом — HF8)
- **P2** — желательное: улучшает опыт, но не блокирует выпуск (разогрев сессий — HF12, расширенный аудит, независимая верификация — HF5.4 — Фаза 2, `vision.md` §2.5)

## Критерии качества FR

Каждое FR должно удовлетворять характеристикам отличного требования (W&B, Chapter 2):

| Характеристика                         | Значение для FR                                                                                             | Как проверить                                                                |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Verifiable** (проверяемость)         | Критерии приёмки измеримы и объективно проверяемы                                                           | Тест, анализ или демонстрация по каждому критерию; покрытие P0/P1 тестами    |
| **Unambiguous** (однозначность)        | Одна интерпретация у всех читателей                                                                         | Ревью; отсутствие «и т. п.», «как правило», «быстро»                         |
| **Complete** (полнота)                 | Вся информация для понимания на месте; пробелы помечены `TBD`                                               | Нет нераскрытых ссылок/терминов; TBD заведены в реестр                       |
| **Necessary** (необходимость)          | Есть ответ «почему это нужно» — трассировка до бизнес-цели                                                  | Цепочка FR → UC → US → HF → G (G1–G7)                                        |
| **Feasible** (реализуемость)           | Реализуемо в рамках известных ограничений (runtime-адаптеры, `@aif/runtime`, `@aif/data`, `vision.md` §2.7) | Оценка разработкой/архитектурой (ADR)                                        |
| **Prioritized** (приоритизированность) | Указан приоритет P0/P1/P2                                                                                   | Наличие поля «Приоритет»                                                     |
| **Correct** (корректность)             | Описывает реальную потребность, не конфликтует с породившим UC                                              | Сверка с UC и `vision.md` §2.2; для `as is` — сверка поведения с реализацией |

**Набор FR** должен быть: **complete** (покрытие всех доменов UC по мере их определения — см. «Текущее состояние»), **consistent** (нет противоречий между FR и NFR), **modifiable** (уникальные ID, изменения отслеживаются), **traceable** (backward: FR → UC → US → vision; forward: FR → тесты/реализация).

## Типичные дефекты FR при ревью

Чек-лист валидации (W&B defect checklist):

| Дефект                   | Признак                                                                   | Действие                                  |
| ------------------------ | ------------------------------------------------------------------------- | ----------------------------------------- |
| Неполнота                | Описание не покрывает все потоки UC                                       | Дополнить или пометить `TBD`              |
| Неоднозначность          | Разные читатели понимают по-разному                                       | Переформулировать, убрать размытые слова  |
| Противоречивость         | Конфликт с другим FR, UC или NFR                                          | Согласовать, зафиксировать решение        |
| Непроверяемость          | Критерий приёмки нельзя объективно проверить                              | Ввести измеримую метрику/условие          |
| Нереализуемость          | Противоречит ограничениям платформы (runtime-адаптеры, модульный монолит) | Пересмотреть или вынести в ADR/NFR        |
| Нет источника/приоритета | Отсутствует трассировка или P0–P2                                         | Восстановить по UC и vision.md            |
| Gold plating             | Функциональность «на всякий случай», не выводимая из UC                   | Удалить или понизить до P2 с обоснованием |

## Специфика проекта

- **Ядро — контекст исполнения**: FR описывают поведение системы AIF Handoff на стороне ядра (api + agent + coordinator). Система работает как модульный монолит: HTTP-сервер (Hono, порт 3009), React SPA (Vite, порт 5180), agent-coordinator (node-cron, цикл 30 с) и WebSocket-сервер для real-time обновлений. Внешние AI-провайдеры (Claude, Codex, OpenRouter) — внешние системы; их внутренние функции в FR не описываются.

- **Runtime — единственный порт к AI**: все вызовы AI-провайдеров проходят через `@aif/runtime` — слой абстракции с единым контрактом (`RuntimeAdapter`), реестром (`RuntimeRegistry`) и системой разрешения профилей. Взаимодействие с runtime моделируется как ACL. FR, описывающие интеграцию с runtime, не дублируют контракт адаптера — контракт ведётся в коде пакета `@aif/runtime`.

- **Координатор — единый оркестратор**: Coordinator (node-cron, `packages/agent/src/coordinator.ts`) опрашивает БД каждые 30 секунд, выбирает задачи, готовые к переходу, и запускает соответствующих субагентов (planner, implementer, reviewer) через выбранный runtime-адаптер. FR pipeline описывают поведение этого цикла, а не детали реализации node-cron или внутренней маршрутизации.

- **Домены FR совпадают с доменами UC**: домены и поддомены FR заимствованы из [use-cases/README.md](../use-cases/README.md) (L1/L2), что обеспечивает прямую трассировку FR → UC. US — язык бизнеса: UC (анализ) выводятся из US, а FR детализируют UC; на FR US трассируются через UC.

- **Функция, а не механизм**: по принципу `vision.md` §2.2 требования описывают результаты, ценные для пользователя (роли из §3.1); каналы (REST API, WebSocket, worktree, `@aif/runtime`, `@aif/data`) — механизмы, они указываются метаданными `**Канал:**` в UC, а не становятся доменами FR.

- **Готовые компоненты**: VCS-интеграция (GitHub REST API, GitLab REST API) — готовые клиенты в `packages/agent/src/githubWorkflow.ts` и `gitlabWorkflow.ts`. FR описывают поведение системы как интегратора готовых клиентов, а не разработку самих клиентов.

- **События предметной области**: `TaskCreated`, `TaskStageChanged`, `TaskGatePassed`, `TaskOwnershipTransferred`, `TaskEscalated`, `RuntimeCallRecorded` и др. — триггеры каскадов в системе (например, прохождение гейта → `TaskGatePassed` → `TaskStageChanged`). FR должны учитывать эти каскады. Каталог событий — `domain/domain-events.md`.

- **Архитектурная изоляция**: данные проходят через `@aif/data` — централизованный слой доступа к БД. Lint-правила блокируют прямой импорт `@aif/shared/src/db` из api/agent/runtime. FR не должны предписывать обход этой изоляции.

- **Классификация `as is` vs `to be`**: FR наследуют класс породившего UC. `as is`-FR фиксируют фактическое поведение системы и не включают гарантий, не подтверждённых этим поведением; `to be`-FR описывают целевую capability с пометкой фазы roadmap (`vision.md` §2.5).

- **NFR — границы качества**: NFR из [nonfun-req/](../nonfun-req/README.md) задают измеримые границы качества (производительность, доступность, безопасность, совместимость) поверх FR; FR не дублируют NFR.

- **Бизнес-правила отдельно от FR**: политики и ограничения (`BR-*`) хранятся в [business-rules/](../business-rules/README.md) как enterprise-level актив (W&B) и переиспользуются всеми артефактами; FR ссылаются на `BR-*`, но не включают их текст.
