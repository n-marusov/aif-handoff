# Нефункциональные требования — AIF Handoff: система автономного управления задачами

В этой директории хранятся формализованные нефункциональные требования (NFR) к системе **AIF Handoff — автономное управление задачами** (`aif-handoff`): модульному монолиту на Turborepo, реализующему hand-off-конвейер с AI-субагентами через подключаемые runtime-адаптеры. NFR задают измеримые границы качества (производительность, доступность, безопасность, совместимость, наблюдаемость) и ограничения на архитектурные решения поверх функциональных требований из `fun-req/`.

Каталог **системный**: NFR описывают ограничения системы AIF Handoff как целого. Внешние AI-провайдеры (Claude Agent SDK, Codex, OpenRouter), VCS-платформы (GitHub, GitLab) и веб-браузер — внешние системы; их NFR вне контура.

Методологическая основа: Software Requirements Engineering (Wiegers & Beatty, 3rd ed.) — трёхуровневая модель требований (business → user → functional/nonfunctional) и цикл разработки требований (Elicitation → Analysis → Specification → Validation). NFR покрывают два класса из таксономии W&B: **атрибуты качества** (измеримые свойства: производительность, доступность, безопасность) и **ограничения** (на архитектурные решения: runtime-адаптеры, СУБД, протоколы). Отличие NFR от бизнес-правил — в [business-rules/README.md](../business-rules/README.md): политики и стандарты организации фиксируются как `BR-*`, ограничения качества и дизайна — как NFR.

## Иерархия требований

Требования организованы по трём уровням (W&B: Business / User / Functional requirements); NFR — артефакт уровня детализации функциональных требований:

```
vision.md — бизнес-требования (Business): SMART-цели G1–G7, проблемы P1–P8, функции HF1–HF12, MVP (§2.4), roadmap (§2.5), ограничения (§2.6)
  └─ use-cases/ — прецеденты использования (User): детализация пользовательских сценариев (UC, домены pipeline/dashboard/runtime/...)
       ├─ fun-req/     — функциональные требования (FR): детализация UC → REQ-FR-*
       ├─ nonfun-req/  — нефункциональные требования (NFR): границы качества поверх FR → REQ-NFR-*
       ├─ business-rules/ — бизнес-правила (BR): политики и ограничения → BR-*
       └─ domain/      — DDD-модель: контексты, агрегаты, события, словарь данных
```

Связи между артефактами:

- **NFR задают измеримые границы качества** для FR и архитектурных решений: NFR выводятся из бизнес-целей (G1–G7), проблем (P1–P8), ограничений (§2.6) и допущений (§2.7) `vision.md`, а также из политик `BR-*`, а не из UC.
- **NFR не дублируют функциональность**: поведение описывают FR и UC; NFR ограничивают его качество. Если ограничение относится к конкретной функции/FR, NFR ссылается на неё (перекрёстная трассировка FR ↔ NFR).
- **NFR не порождают пользовательских историй**: US — язык бизнеса (первичный пользовательский артефакт); UC (анализ) выводятся из US, границы качества историями не описываются.
- **Бизнес-правила (`BR-*`) — отдельный актив** (W&B: enterprise-level asset): политики и ограничения хранятся в [business-rules/](../business-rules/README.md); NFR ссылаются на них по ID, но не включают их текст (например, `BR-trigger.automation.pipeline`, `BR-fact.auth.roles`).
- **Ограничения-констрейнты ≠ бизнес-правила**: ограничения на архитектурные решения (выбор СУБД, протоколов, инфраструктуры развёртывания) фиксируются в NFR, а не в `BR-*`.

## NFR в жизненном цикле требований

NFR выявляются на стадии **Analysis** (шаг 7 процесса W&B: «analyze requirements for quality attributes and business rules») и специфицируются на стадии **Specification**. Стадии цикла W&B применяются к NFR так:

| Стадия            | Что делаем с NFR                                                                                                                                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Elicitation**   | Выявление атрибутов качества и ограничений из бизнес-целей (G1–G7), проблем (P1–P8), ограничений §2.6 и допущений §2.7 `vision.md`, приоритетов проекта (§3.2), фаз roadmap (§2.5) и правил `BR-*`                      |
| **Analysis**      | Отделение NFR от FR и бизнес-правил; определение относительной важности атрибутов качества (trade-offs): безопасность доступа, безотказность конвейера, производительность polling — критические факторы (§3.2)         |
| **Specification** | Оформление по шаблону: ID, приоритет, источник, ключевая функция, описание, измеримые критерии приёмки (метрика + целевое значение); целевые значения закрывают пробелы `[TBD-VM*]`/`[TBD-VT*]` из `vision.md` §1.3–1.4 |
| **Validation**    | Проверка измеримости (метрика + целевое значение), ревью (чек-лист дефектов ниже), тесты производительности/безопасности/доступности                                                                                    |

## Формат идентификатора NFR

```
REQ-NFR-<area>.<qualifier>.<attribute>
```

| Часть         | Описание                                               | Допустимые значения                                                                      |
| ------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| **area**      | Область ограничения                                    | `api` · `security` · `data` · `infra` · `ui` · `ops` · `integration` · `process` · `doc` |
| **qualifier** | Категория качества                                     | `performance` · `availability` · `observability` · `compliance` · `maintainability`      |
| **attribute** | Конкретный атрибут качества в kebab-case (ограничение) | свободная семантическая метка                                                            |

### Правила именования

1. Только **kebab-case**, без цифр и индексов.
2. Область и квалификатор — строго из перечней допустимых значений таксономии выше.
3. Функция/домен в ID не входят: функция указывается полем «Ключевая функция» (HF1–HF12) файла NFR, домен/поддомен (pipeline, dashboard, ...) — в поле «Домен», если применимо.
4. Идентификатор устойчив: добавление или удаление NFR не меняет ID существующих.

### Примеры идентификаторов

Идентификаторы NFR строятся по схеме `REQ-NFR-<area>.<qualifier>.<attribute>`; примеры корректных ID для типовых ограничений системы:

| REQ-ID (проект)                                              | Описание                                                                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `REQ-NFR-api.availability.websocket-reconnect`               | Авто-восстановление WebSocket-соединения после временного разрыва: состояние дашборда не теряется, команды не дублируются   |
| `REQ-NFR-security.compliance.session-auth`                   | 100% API-запросов к задачам и проектам требуют аутентификации; неаутентифицированный доступ возвращает 401                  |
| `REQ-NFR-api.performance.coordinator-polling-latency`        | Coordinator обнаруживает задачу, готовую к переходу, не более чем за 30 с (цикл polling)                                    |
| `REQ-NFR-ops.observability.audit-trail-completeness`         | 100% переходов задач между стадиями фиксируются в иммутабельном аудите с актором и временем                                 |
| `REQ-NFR-data.compliance.task-state-persistence`             | Состояние задачи не теряется при перезапуске API или coordinator: SQLite-БД восстанавливается в согласованном состоянии     |

## Правила оформления

1. **Один файл — одно нефункциональное требование.**
2. **Имя файла**: `REQ-NFR-<area>.<qualifier>.<attribute>.md`.
3. **Язык**: русский. Технические термины — на английском.
4. **Обязательные поля**:
   - **Приоритет:** `P0` / `P1` / `P2`
   - **Источник:** ссылка на бизнес-цель (G1–G7), проблему (P1–P8), ограничение (§2.6), допущение (§2.7) из `vision.md` и/или правило `BR-*`; для NFR, восстановленных из реализации, — пометка «реверс-инжиниринг кода»
   - **Ключевая функция:** ссылка на функцию/подфункцию HF1–HF12 из `vision.md` §2.2 (если применимо)
   - **Описание:** суть ограничения качества
   - **Критерии приёмки:** измеримые условия выполнения — метрики и целевые значения (без метрики требование не проверяемо)
5. **Рекомендуемые поля** (атрибуты требований, W&B Chapter 27):
   - **Статус:** `proposed` → `approved` → `implemented` → `verified` → `deleted` (отслеживание статуса)
   - **Связанные требования:** ссылки на родственные FR/`NFR-*` и `BR-*` (перекрёстная трассировка)
   - **Класс:** `as is` (ограничение подтверждено реализацией) / `to be` (ограничение по roadmap §2.5)
   - **Домен L1:** домен UC, к которому применимо NFR (pipeline, dashboard, runtime, ...)
6. **TBD-флаг**: пробелы в требовании помечаются `TBD` и фиксируются в [open-questions.md](../open-questions.md) — требование не считается готовым, пока TBD не закрыт.
7. **Трассируемость**: каждый NFR ссылается на источник в поле «Источник» и функцию в поле «Ключевая функция» (HF1–HF12). Forward-трассировка: NFR → тесты (производительность, безопасность, доступность) и реализация.
8. **Независимость от реализации**: файлы требований не содержат ссылок на код — ни путей (`packages/...`), ни имён символов реализации. Связи NFR с реализацией фиксируются вне файлов требований (трассировка).

## Приоритеты

Приоритет определяет порядок реализации (W&B: prioritization по ценности, стоимости и риску) и относительную важность атрибутов качества при trade-offs (§3.2 `vision.md`):

- **P0** — критическое: без него MVP невозможен или небезопасен (аутентификация всех запросов, иммутабельный аудит переходов, целостность состояния задач после перезапуска)
- **P1** — важное: ключевое ограничение качества (авто-восстановление WebSocket, resilience coordinator при недоступности VCS, наблюдаемость ошибок runtime)
- **P2** — желательное: улучшает качество, но не блокирует выпуск (производительность polling под нагрузкой, расширенная телеметрия, rate-limit на уровне адаптера — Фаза 2, `vision.md` §2.5)

## Критерии качества NFR

Каждое NFR должно удовлетворять характеристикам отличного требования (W&B, Chapter 2); для NFR решающая характеристика — **проверяемость**: без метрики и целевого значения NFR не является требованием:

| Характеристика                         | Значение для NFR                                                                       | Как проверить                                          |
| -------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **Verifiable** (проверяемость)         | Метрика и целевое значение заданы («100% запросов», «≤ N с», «0 потерянных переходов») | Замер/тест по критериям приёмки                        |
| **Unambiguous** (однозначность)        | Конкретные числа вместо «быстро», «надёжно», «удобно»                                  | Ревью: отсутствие размытых формулировок                |
| **Complete** (полнота)                 | Охвачены все режимы/сценарии, к которым применимо (нормальный, сбой, восстановление)   | Перечень сценариев полон                               |
| **Necessary** (необходимость)          | Выводится из бизнес-цели/проблемы/ограничения/правила                                  | Трассировка NFR → G/P → §2.6 → BR                      |
| **Feasible** (реализуемость)           | Целевое значение достижимо в рамках архитектуры (SQLite, node-cron, `@aif/runtime`)    | Оценка разработкой ([ADR](../adr/README.md), прототип) |
| **Prioritized** (приоритизированность) | Указан приоритет P0/P1/P2                                                              | Наличие поля «Приоритет»                               |
| **Correct** (корректность)             | Не конфликтует с FR, BR и другими NFR                                                  | Сверка; учёт trade-offs атрибутов качества (§3.2)      |

**Набор NFR** должен быть: **complete** (покрытие всех значимых атрибутов качества — см. «Текущее состояние»), **consistent** (нет противоречий между атрибутами — trade-offs разрешены и зафиксированы), **modifiable** (уникальные ID, изменения отслеживаются), **traceable** (backward: NFR → G/P/§2.6/BR; forward: NFR → тесты/реализация).

## Типичные дефекты NFR при ревью

Чек-лист валидации (W&B defect checklist). Главный дефект NFR — **непроверяемость**:

| Дефект                   | Признак                                                                                 | Действие                                                     |
| ------------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Непроверяемость          | Нет метрики/целевого значения («быстрая работа», «высокая надёжность»)                  | Ввести измеримый критерий или удалить                        |
| Неоднозначность          | «Надёжный», «удобный», «минимальный» без числа                                          | Конкретизировать числом или границей                         |
| Противоречивость         | Конфликт с FR, BR или другим NFR (trade-off не разрешён)                                | Согласовать, зафиксировать решение в [ADR](../adr/README.md) |
| Неполнота                | Покрыта не вся область (сценарий сбоя, восстановления, нагрузки)                        | Дополнить или пометить `TBD`                                 |
| Нереализуемость          | Целевое значение недостижимо в рамках архитектуры (SQLite, node-cron, runtime-адаптеры) | Пересмотреть цель, обосновать в [ADR](../adr/README.md)      |
| Дублирование BR/FR       | Ограничение-политика продублировано текстом из `BR-*`; функциональность — из FR         | Оставить ссылку на `BR-*`/FR, убрать текст                   |
| Нет источника/приоритета | Отсутствует трассировка или P0–P2                                                       | Восстановить по G/P/§2.6/BR                                  |
| Gold plating             | Избыточное качество без бизнес-обоснования                                              | Удалить или понизить до P2                                   |

## Специфика проекта

- **Ядро — контекст исполнения**: NFR описывают ограничения AIF Handoff на стороне ядра (api + agent + coordinator). Система работает как модульный монолит: HTTP-сервер (Hono, порт 3009), React SPA (Vite, порт 5180), agent-coordinator (node-cron, цикл 30 с) и WebSocket-сервер для real-time обновлений. Внешние AI-провайдеры (Claude, Codex, OpenRouter) и VCS-платформы (GitHub, GitLab) — внешние системы; их NFR вне контура.

- **Runtime — единственный порт к AI**: все вызовы AI-провайдеров проходят через `@aif/runtime` — слой абстракции с единым контрактом (`RuntimeAdapter`), реестром и профилями. NFR области `api` фиксируют доступность и поведение этого канала: таймауты, ретраи, корректная обработка ошибок адаптеров.

- **SQLite — единственное хранилище**: данные хранятся в SQLite (better-sqlite3 + drizzle-orm), ФС — блокирующий synchronus I/O. NFR области `data` обязаны учитывать границы SQLite (однопоточная запись, размер БД, конкурентный доступ) и не требовать СУБД класса PostgreSQL.

- **Координатор — единый оркестратор**: Coordinator (node-cron, `packages/agent/src/coordinator.ts`) опрашивает БД каждые 30 секунд. NFR производительности обязаны учитывать, что polling-цикл — единственный механизм обнаружения готовых к переходу задач, и не требовать event-driven архитектуры для этого сценария.

- **Атрибуты качества и ограничения** (W&B таксономия): NFR покрывают измеримые атрибуты качества (доступность WebSocket, производительность polling, наблюдаемость аудита) и ограничения на архитектурные решения (SQLite, node-cron, `@aif/data` как единый слой доступа к БД). Ограничения фиксируются в NFR, а не в FR и не в `BR-*`.

- **Метрики-прокси, а не «отсутствие инцидентов»**: безопасность и корректность измеряются проверяемыми показателями — 100% запросов с аутентификацией (G1), 100% переходов с аудитом (G3), ноль потерянных при перезапуске (G5); целевые значения метрик-пробелов `vision.md` (`[TBD-VM1]`–`[TBD-VM7]`) закрепляются NFR.

- **Безопасность эшелонированно и по фазам roadmap**: аутентификация и session management (`BR-auth.*`, `BR-audit.*`) — MVP; расширенный RBAC, rate-limit на уровне адаптера, усиление аудита — Фаза 2 (§2.5). NFR `to be` помечаются классом целевого состояния и фазой roadmap.

- **Архитектурная изоляция**: данные проходят через `@aif/data` — централизованный слой доступа к БД. Lint-правила блокируют прямой импорт `@aif/shared/src/db` из api/agent/runtime. NFR не должны предписывать обход этой изоляции.
