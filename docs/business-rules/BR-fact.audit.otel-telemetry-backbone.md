# BR-fact.audit.otel-telemetry-backbone — Единый сбор телеметрии на OpenTelemetry

> Телеметрия исполнения всех процессов системы собирается как три типа сигналов OpenTelemetry (трассировки, метрики, логи) и доставляется через OTel Collector в хранилища; журналы `pino` остаются источником, их доставка в стек — аддитивный поток.

## Правило

Каждый исполняемый процесс (`api`, `agent`, `mcp`, `web`) эмитирует трассировки, метрики и логи по стандарту OpenTelemetry и отправляет их по OTLP в единый OTel Collector. Collector — единственная точка применения политик (нормализация, сокрытие чувствительных данных, ограничение кардинальности, выборка); приложение о хранилищах не знает. Хранение — self-hosted: Tempo (трассировки), Loki (логи), Prometheus (метрики), Grafana (совмещение).

## Детализация

- Сбор выключен по умолчанию; включается явными флагами окружения.
- Экспорт non-throwing: сбой хранилища или collector не влияет на выполнение конвейера; при недоступности наблюдаемости логи остаются в локальном выводе.
- Только OTLP-экспортёры; console-экспорт запрещён, stdout в stdio-режиме MCP зарезервирован под JSON-RPC.
- `pino` остаётся API и источником истины журналирования; OTLP-доставка логов — второй поток к существующему назначению.

## Обоснование

Единый стандарт даёт сквозную коррелированную картину исполнения без ручной стыковки четырёх разнородных каналов; политики меняются конфигурацией collector, а не релизом; AI-контур читает те же нормализованные сигналы, что и Grafana. Стандарт открыт и не привязывает к вендору.
