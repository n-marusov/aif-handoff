# BR-task-lifecycle.transitions — Допустимость переходов между стадиями

> Не все переходы между стадиями разрешены. Допустимость перехода определяется текущей стадией, владельцем задачи и ролью действующего субъекта.

## Правило

Переход задачи в новую стадию разрешён только при одновременном выполнении условий:

1. **Стадия-источник** входит в перечень допустимых для запрошенного действия.
2. **Владелец задачи** (AI или человек) допускает это действие.
3. **Действующий субъект** авторизован (в режиме участников) и, для роли Member, назначен на задачу.
4. **Состояние задачи** не изменилось с момента, когда оно было прочитано субъектом.

При нарушении любого условия переход отклоняется без частичных изменений; субъект получает структурированный отказ.

## Детализация

- Действия выражаются событиями задачи, а не произвольной сменой стадии: `start_ai`, `start_human_work`, `mark_plan_ready`, `start_implementation`, `publish_plan`, `approve_plan`, `request_plan_changes`, `submit_implementation`, `complete_review`, `request_review_changes`, `pass_verification`, `fail_verification`, `request_replanning`, `fast_fix`, `approve_done`, `request_changes`, `retry_from_blocked`.
- **AI-владелец**: задача продвигается автоматическим агентом.
- **Человек-владелец**: доступен собственный набор действий; действия, требующие AI, отклоняются с признаком «требуется передача задачи AI».
- **Участник** не изменяет стадию напрямую — только через явное действие задачи.
- **Агент** изменяет стадию только у задачи, находящейся под владением AI.
- Каждое действие проверяется против снимка задачи (стадия, авто-режим, владелец, назначения) и фиксируется атомарно с проверкой неизменности стадии.

## Обоснование

Формальная модель переходов исключает обход гейтов, гарантирует, что результат не продвигается без проверки, и делает поведение одинаковым для API, слоя данных и интерфейса.
