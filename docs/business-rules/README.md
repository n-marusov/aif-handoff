# Business Rules — AIF Handoff

> Политики, стандарты и регуляции, управляющие жизненным циклом задач, правами участников и автоматическим конвейером обработки.

Каталог бизнес-правил (`BR-*`) — единый источник политик продукта. Каждое правило — декларативная формулировка в терминах предметной области, без указания способа реализации. Каталог разбит на отдельные файлы `BR-<тип>.<домен>.<тег>.md`; этот README служит методологией, форматом и навигацией.

---

## Principles

| Принцип                             | Описание                                                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **Правило — не функция**            | Правило описывает политику или ограничение, а не способ реализации. Функциональные требования выводятся из правил, но не совпадают с ними. |
| **Enterprise-level актив**          | Правила принадлежат продукту, а не отдельной реализации. Они переживают изменения кода и архитектуры.                                      |
| **Декларативная формулировка**      | Правило формулируется в терминах бизнеса: «Задача не может быть принята без проверки», а не «вызывать validateTask() при approve».         |
| **Устойчивые идентификаторы**       | ID правила не меняется при добавлении, изменении или удалении других правил.                                                               |
| **Трассируемость**                  | Реализация ссылается на правило по ID; правило не содержит деталей реализации.                                                             |
| **Хранение отдельно от реализации** | Правила ведутся в каталоге `business-rules/`; код и документация на них ссылаются по ID.                                                   |

## Таксономия бизнес-правил (Wiegers & Beatty)

По **Software Requirements, 3rd ed. (Microsoft Press, 2013)**, бизнес-правила классифицируются по пяти типам. Каждое правило в каталоге `BR-*` должно относиться ровно к одному из них.

| Тип                                       | Определение                                                                                                                                            | Пример из AIF Handoff                                                                                                                                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fact** (факт)                           | Утверждение истины о бизнесе; факт отношения между бизнес-сущностями. Правило не предписывает действие, а фиксирует неотъемлемое свойство домена.      | «У задачи ровно один владелец — агент или человек» (`BR-fact.ownership.assignment`)                                                                                                                                     |
| **Constraint** (ограничение)              | Условие, которое должно соблюдаться. Ограничивает допустимые состояния, переходы или атрибуты бизнес-объектов.                                         | «Задача не может быть принята без проверки»; «В проекте одна задача за раз, если нет изоляции» (`BR-constraint.automation.concurrency`)                                                                                 |
| **Action trigger** (триггер действия)     | Условие вида WHEN–THEN: при наступлении определённого события или состояния система (автоматика) должна выполнить предписанное действие.               | «При приближении к лимиту провайдера — упреждающая блокировка» (`BR-trigger.automation.runtime-limit-gate`); «Задача в Backlog запускается автоматически в назначенный момент» (`BR-trigger.task-lifecycle.scheduling`) |
| **Inference** (вывод)                     | Правило вида IF–THEN, выводящее новое знание или классификацию из существующих фактов. Не предписывает действие, а устанавливает логическое следствие. | «Если задача под владением человека — автоматизация её не обрабатывает» (`BR-inference.ownership.automation-eligibility`); «По умолчанию — две роли: Admin и Member» (`BR-fact.auth.roles`)                             |
| **Derivation / Calculation** (вычисление) | Математическое правило, определяющее, как значение одного атрибута выводится из других. Как правило, это формулы, скоринги, агрегации.                 | «Глубина конвейера проекта — настраиваемый параметр»; лимиты учёта runtime — вычисление остатка по профилю (TBD в `BR-trigger.automation.runtime-limit-gate`)                                                           |

### Правила отнесения к типу

1. **Один тип — одно правило.** Если формулировка содержит элементы нескольких типов, разделить на отдельные правила (каждое — своя декларация).
2. **Fact vs. Constraint:** факт фиксирует отношение, ограничение — запрет или обязательство. «Задача принадлежит проекту» — факт; «Задача не может быть без проекта» — ограничение.
3. **Trigger vs. Inference:** триггер предписывает действие (WHEN–THEN), вывод — только новое знание (IF–THEN → факт). «Если превышен лимит — заблокировать» — триггер; «Если превышен лимит — задача High Risk» — вывод.
4. **Derivation vs. Trigger:** вычисление — функция от известных величин; триггер — реакция на событие или состояние.

## Иерархия требований

```
business-rules/              — бизнес-правила продукта (BR-*): политики, стандарты, регуляции
  ├── README.md              — методология, формат, навигация
  └── BR-<тип>.<домен>.<тег>.md    — отдельные правила (по одному файлу на правило)
        └── управляют производными артефактами:
              docs/*             — документация продукта (архитектура, API, конфигурация, провайдеры)
              docs/use-cases/*   — прецеденты использования (UC) ссылаются на BR-* по ID
              docs/adr/*         — архитектурные решения трассируются на BR-*
```

**Цепочка трассируемости:** `Vision (HF1–HF12) → US (§2.2) → UC → BR → FR → ADR → код`.

## Формат идентификатора BR

```
BR-<тип>.<домен>.<семантический-тег>
```

| Часть                 | Описание                                                                                       | Пример                                                              |
| --------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **тип**               | Тип по таксономии Wiegers & Beatty: `fact`, `constraint`, `trigger`, `inference`, `derivation` | `fact`, `constraint`, `trigger`, `inference`                        |
| **домен**             | Предметная область правила                                                                     | `task-lifecycle`, `ownership`, `auth`, `automation`, `git`, `audit` |
| **семантический-тег** | Англоязычная метка в kebab-case                                                                | `stages`, `transitions`, `roles`, `pipeline`, `branch-naming`       |

### Правила именования

1. Только kebab-case, без цифр и индексов.
2. Тип — один из пяти по Вигерсу (первичная ось таксономии).
3. Домен — из списка доменов (вторичная ось каталога).
4. Семантический тег — свободная метка, отражающая суть правила.
5. Идентификатор устойчив: не меняется при добавлении или удалении других правил.

## Формат файла правила

Каждый файл `BR-<тип>.<домен>.<тег>.md` содержит:

| Секция                                                   | Обязательность | Описание                                                           |
| -------------------------------------------------------- | -------------- | ------------------------------------------------------------------ |
| Метаданные (`ID`, `Тип`, `Домен`, `Статус`, `Приоритет`) | Обязательно    | Устойчивый идентификатор и атрибуты правила.                       |
| `## Правило` / `## Формулировка`                         | Обязательно    | Декларативная формулировка политики в терминах предметной области. |
| `## Детализация`                                         | Рекомендуется  | Уточняющие условия и ограничения правила (без деталей реализации). |
| `## Обоснование`                                         | Рекомендуется  | Бизнес-смысл: почему правило существует.                           |
| `## Трассируемость`                                      | Обязательно    | Ссылки на документацию (origin) и на реализацию (forward trace).   |
| `## Связанные правила`                                   | Рекомендуется  | Связи с другими `BR-*` (совместимость набора).                     |
