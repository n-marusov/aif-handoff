# Business Rules — AIF Handoff

> Политики, стандарты и регуляции, управляющие жизненным циклом задач, правами участников и автоматическим конвейером обработки.

Каталог бизнес-правил (`BR-*`) — единый источник политик продукта. Каждое правило — декларативная формулировка в терминах предметной области, без указания способа реализации.

---

## Principles

| Принцип                             | Описание                                                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **Правило — не функция**            | Правило описывает политику или ограничение, а не способ реализации. Функциональные требования выводятся из правил, но не совпадают с ними. |
| **Enterprise-level актив**          | Правила принадлежат продукту, а не отдельной реализации. Они переживают изменения кода и архитектуры.                                      |
| **Декларативная формулировка**      | Правило формулируется в терминах бизнеса: «Задача не может быть принята без проверки», а не «вызывать validateTask() при approve».         |
| **Устойчивые идентификаторы**       | ID правила не меняется при добавлении, изменении или удалении других правил.                                                               |
| **Трассируемость**                  | Реализация ссылается на правило по ID; правило не содержит деталей реализации.                                                             |
| **Хранение отдельно от реализации** | Правила ведутся в каталоге `business-rules/`; код и документация на них ссылаются по ID.                                                   |

---

## Иерархия требований

```
business-rules/          — бизнес-правила продукта (BR-*): политики, стандарты, регуляции
  └── README.md          — методология, формат, навигация
  └── BR-<тип>.<тег>.md — отдельные правила (по одному файлу на правило)
        └── управляют производными артефактами:
              docs/*     — документация продукта (архитектура, API, конфигурация)
```

## Task Lifecycle

Жизненный цикл задачи — последовательность стадий, через которые проходит задача от создания до завершения.

### BR-task-lifecycle.stages

Задача последовательно проходит стадии:

| Стадия       | Назначение                                                         |
| ------------ | ------------------------------------------------------------------ |
| Backlog      | Исходное состояние. Задача зарегистрирована, но не взята в работу. |
| Planning     | Разработка плана реализации.                                       |
| Improve      | Доработка плана по результатам ревью или репланирования.           |
| Plan Ready   | План готов к реализации, ожидает назначения.                       |
| Plan Review  | План опубликован и ожидает утверждения перед началом реализации.   |
| Implementing | Выполнение работ по задаче.                                        |
| Verify       | Проверка результата на соответствие критериям качества.            |
| Review       | Ревью результата.                                                  |
| Blocked      | Выполнение приостановлено из-за внешней зависимости.               |
| Done         | Работы завершены, результат доступен для приемки.                  |
| Accepted     | Задача принята заказчиком. Финальное состояние.                    |

### BR-task-lifecycle.transitions

Не все переходы между стадиями разрешены. Допустимость перехода определяется:

- **Текущей стадией задачи** — переход возможен только из определённых стадий.
- **Владельцем задачи** — автоматизированный агент и человек имеют разные наборы разрешённых действий.
- **Участниками и их ролями** — в режиме участников действие должно быть авторизовано.

### BR-task-lifecycle.blocked

Задача может быть приостановлена на любой стадии при наличии внешней блокировки. При возобновлении задача возвращается на стадию, с которой была заблокирована.

### BR-task-lifecycle.done-to-accepted

Задача в стадии Done может быть принята (Accepted) или возвращена на доработку (Implementing). Приёмка — финальное решение, после которого задача не может быть изменена.

## Ownership & Handoff

### BR-ownership.assignment

Каждая задача имеет одного владельца — автоматизированного агента или человека-участника. Владелец определяет, кто может продвигать задачу по стадиям.

### BR-ownership.handoff

Владение задачей может быть передано между участниками или между участником и агентом. Передача возможна только при соблюдении правил авторизации.

### BR-ownership.executor-history

Система ведёт историю владения задачей: кто, когда и по какой причине получил владение. История неизменяема.

### BR-ownership.assignee

Задача может иметь одного или нескольких исполнителей (assignees), назначенных для выполнения работ. Назначение не меняет владельца задачи.

## Participant Authorization

### BR-auth.roles

Участники системы имеют роли, определяющие объём доступных действий:

| Роль   | Действия                                                                                             |
| ------ | ---------------------------------------------------------------------------------------------------- |
| Admin  | Любые действия над любой задачей, управление назначениями, управление участниками.                   |
| Member | Действия только над задачами, к которым участник назначен. Самоназначение на задачи без исполнителя. |

### BR-auth.admin-privileges

Администратор может выполнять любые действия над задачами независимо от владельца и назначения.

### BR-auth.member-scope

Участник с ролью Member может:

- Выполнять действия только над задачами, к которым он назначен и назначение активно.
- Самостоятельно назначиться на задачу с человеческим владельцем, если у задачи нет исполнителей.
- Видеть и комментировать любые задачи в проекте.

### BR-auth.task-isolation

Участник не может действовать над задачей, владельцем которой является автоматизированный агент, если участник не является администратором.

## Project Structure

### BR-project.task-scope

Каждая задача принадлежит ровно одному проекту. Проект изолирует задачи от задач других проектов: стадии, участники и настройки определяются в контексте проекта.

### BR-project.runtime-profiles

Каждый проект может иметь профили для различных этапов обработки задачи (планирование, выполнение, ревью, чат). Если профиль не задан на уровне проекта, используется общесистемный профиль.

## Automation Policy

### BR-automation.pipeline

Система может автоматически продвигать задачи по стадиям жизненного цикла. Для каждой стадии определены условия входа и выхода.

### BR-automation.auto-queue

Задачи могут автоматически переходить из одной стадии в следующую при наступлении определённых условий (завершение предыдущей стадии, наличие готового результата).

### BR-automation.plan-review-gate

Перед началом реализации план может требовать утверждения через внешнюю систему ревью (публикация с запросом утверждения). Без утверждения реализация не начинается.

## Git Operations

### BR-git.branch-naming

Работа над задачей ведётся в отдельной ветке. Имя ветки формируется по конвенции проекта: префикс ветки и идентификатор задачи.

### BR-git.commit-conventions

Коммиты, относящиеся к артефактам планирования, используют выделенный префикс сообщения. Конвенция определяется на уровне проекта.

### BR-git.convention-resolution

Конвенции именования веток и коммитов разрешаются в порядке приоритета: явные правила проекта → настройки проекта → общесистемные значения по умолчанию.

## Audit & Compliance

### BR-audit.immutable-trail

Все действия над задачами (изменение стадии, передача владения, назначение, комментарии) записываются в неизменяемый журнал аудита. Записи не могут быть изменены или удалены.

### BR-audit.actor-identity

Каждая запись аудита содержит идентификатор субъекта действия: участник (с именем) или автоматизированный агент.

### BR-audit.state-snapshot

Аудит фиксирует состояние задачи на момент действия: стадия, владелец, назначения. Это позволяет восстановить историю задачи в любой момент.

## Формат идентификатора BR

```
BR-<домен>.<семантический-тег>
```

| Часть                 | Описание                        | Пример                                                              |
| --------------------- | ------------------------------- | ------------------------------------------------------------------- |
| **домен**             | Предметная область правила      | `task-lifecycle`, `ownership`, `auth`, `automation`, `git`, `audit` |
| **семантический-тег** | Англоязычная метка в kebab-case | `stages`, `transitions`, `roles`, `pipeline`, `branch-naming`       |

### Правила именования

1. Только kebab-case, без цифр и индексов.
2. Домен — из списка доменов (первичная ось каталога).
3. Семантический тег — свободная метка, отражающая суть правила.
4. Идентификатор устойчив: не меняется при добавлении или удалении других правил.
