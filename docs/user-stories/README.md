# Пользовательские истории — VNC: компонент удалённого управления

В этой директории находятся пользовательские истории (User Stories) компонента **VNC — компонент удалённого управления** (`epc-vnc`) — локального GUI/tray-приложения на кассовом узле, запускающего VNC/RFB 3.8 сервер на базе готового решения (из AC) и обеспечивающего удалённый доступ оператора техподдержки к экрану узла через облако с кодом доступа в обе стороны. Все истории оформлены в формате Gherkin.

**Назначение US.** Пользовательские истории — **язык бизнеса** (первичный пользовательский артефакт): основа для генерации E2E-тестов и для общения с представителями бизнеса. Каждая история описывает ожидаемое поведение системы глазами пользователя на языке, понятном обеим сторонам, и восходит к функции VF1–VF7 из `vision.md`. UC (`use-cases/`) — артефакт анализа: прецедент детализирует историю (акторы, каналы, потоки, постусловия), а FR детализируют UC.

## Структура

- `README.md` — данный файл с описанием требований к разработке пользовательских историй
- `US-<domain>.<subdomain>.<action>.md` — отдельные файлы пользовательских историй с семантическими идентификаторами

## Семантическая классификация US

Идентификаторы пользовательских историй построены по иерархическому принципу, аналогично UC:

```
US-<domain>.<subdomain>.<action>
```

Домен (L1) и поддомен (L2) соответствуют функциям VF1–VF7 `vision.md` и доменам UC, что облегчает навигацию и трассировку (US → UC → FR).

## Формат описания

Все пользовательские истории оформлены единым Gherkin-шаблоном:

```gherkin
@US-<domain>.<subdomain>.<action> @UC-... @P...
Feature: US-<domain>.<subdomain>.<action> <краткое название>

  Background:
    Given <общие предусловия>

  Scenario: <основной пользовательский результат>
    Given <контекст>
    When <действие пользователя или системы>
    Then <ожидаемый результат>
```

### Теги

Каждая история содержит теги:

- `@US-<domain>.<subdomain>.<action>` — семантический идентификатор пользовательской истории
- `@UC-...` — идентификатор прецедента использования (UC) — анализа данной истории
- `@P0`/`@P1`/`@P2` — приоритет (P0 — критический, P1 — важный, P2 — желательный)
- Дополнительные теги для фильтрации по домену: `@remote`, `@local`; по поддомену: `@session`, `@access-code`, `@screen`, `@input`, `@clipboard`, `@files`, `@ssh`, `@tray`

## Требования к разработке пользовательских историй

### 1. Структура и именование

- Каждый файл содержит одну пользовательскую историю или один сквозной сценарий.
- Имя файла соответствует семантическому идентификатору: `US-<domain>.<subdomain>.<action>.md`.
- Файл начинается с заголовка первого уровня (`#`) с полным идентификатором и названием.
- Теги Gherkin указываются в первой строке сценария.
- Идентификатор вешается якорем (`<a id="us-<domain>.<subdomain>.<action>"></a>`) перед заголовком для кросс-ссылок.

### 2. Содержание

- **Background** описывает общие предусловия для всех сценариев истории.
- **Scenario** описывает один конкретный пользовательский результат.
- Шаги `Given` задают контекст и предварительные условия.
- Шаги `When` описывают действие пользователя или системы.
- Шаги `Then` проверяют ожидаемый результат.
- Для проверки альтернативных потоков (негативные сценарии) используется отдельный Scenario.

### 3. Язык

- Все пользовательские истории пишутся **на русском языке**.
- Названия сущностей, свойств и технические идентификаторы — на английском (например, `Node`, `Agent mdl`, `Node ID`, `Access Code`, `VNC Session`, `VNC Management Service`, `VNC Repeater`, `framebuffer`, `repeater`).
- Сообщения об ошибках, возвращаемые системой, указываются в кавычках на языке системы (английский).

### 4. Приоритеты

- **P0** — критические сценарии, без которых MVP невозможен (например, установление защищённой VNC-сессии с двусторонним кодом доступа, передача экрана узла, отсутствие входящих портов на узле).
- **P1** — важные сценарии, закрывающие ключевые потребности пользователей (например, передача состояния и ошибок в платформу, синхронизация буфера обмена, передача файлов, маскирование чувствительных областей экрана).
- **P2** — желательные сценарии, улучшающие пользовательский опыт (например, выбор монитора, отключение/включение картинки оператором, возобновление/отмена передачи файлов, SSH-управление узлом).

### 5. Связи

- US — **язык бизнеса**: каждая история описывает пользовательскую ценность на языке, понятном бизнесу, и восходит к функции VF1–VF7 из `vision.md`.
- UC — артефакт анализа: прецедент детализирует историю (акторы, каналы, основной/альтернативные потоки, постусловия); каждый UC выводится из US и трассируется на неё.
- FR детализируют UC: на FR история трассируется через UC (Vision → US → UC → FR); US напрямую FR не порождают.
- Каждая история должна иметь назначенный приоритет.

### 6. Специфика проекта

- **Узел — контекст исполнения**: истории описывают поведение компонента vnc на кассовом узле клиента. Компонент работает в пользовательской сессии (Windows — сервис `epc-vnc`; Linux — запуск в сессии пользователя), в отличие от фоновых сервисов `mdl`/`upd`. Серверная часть (VNC Management Service, VNC Repeater, Websockify, noVNC) — внешняя система; истории не описывают её внутренние функции — это зона серверной части платформы.
- **mdl — единственный порт в платформу**: команды облака (запуск/остановка, код доступа, настройки) приходят через локальный gRPC `VNCService` (`127.0.0.1:5051`, insecure); состояние (`IDLE`/`LISTENING`/`CONNECTED`) и ошибки передаются обратно. Агент `mdl` — внешняя система (ACL, см. `domain/context-map.md`).
- **Функция, а не механизм**: по принципу `vision.md` §2.2 истории — результаты, ценные для пользователя (роли из §3.1), а не каналы. RFB 3.8, Raw/ZRLE, VNC Authentication, gRPC `VNCService`, TCP-туннель к репитеру (Mode II) — механизмы; они указываются метаданными, а не становятся доменами.
- **Готовое VNC-решение**: VNC/RFB-сервер — готовое решение (из AC, `vision.md` §2.7); истории описывают поведение компонента как интегратора готового решения, разработка/доработка самого VNC-сервера/клиента — вне рамок.
- **События предметной области**: `VncSessionRequested`, `VncAccessCodeConfirmed`, `VncSessionEstablished`, `VncStateChanged`, `VncSessionTerminated`, `VncAccessCodeRotated`, `VncErrorReported`, `FileTransferCompleted` — триггеры каскадов на узле, и истории должны явно описывать эти каскады (например, подключение клиента → `VncSessionEstablished` → `VncStateChanged` (`CONNECTED`) → `SendVNCInfo`). Каталог событий — `domain/domain-events.md`.
- **Спектр платформ**: истории учитывают платформы развёртывания компонента — Windows 7–11, Linux (Ubuntu/Debian, RHEL; Wayland/GStreamer, встраиваемые сборки) и АТОЛ ОС (СТ SIGMA); Android — `[TBD-D2]`, `vision.md` §2.7.
- **Классификация `as is` vs `to be`**: `as is`-истории описывают фактическое поведение компонента; `to be`-истории помечаются target-пометкой и фазой roadmap (`vision.md` §2.6). К неподтверждённым гарантиям относятся: явный TTL сессии, кириллическая раскладка (обработчик ExtendedKeyEvent отключён), выбор монитора, кодировки `tight`/`ContinuousUpdates`, resume/cancel file transfer, SSH (VF7), TLS поверх RFB, RBAC, расширенный аудит, rate limit/replay-защита кодов.

### 7. Accessibility (доступность)

- Доступность GUI в системном трее (компонент `vnc`, VF5.4) — сквозное требование: истории `US-local.tray.*` должны учитывать screen reader (NVDA / VoiceOver) и keyboard-only навигацию.
- Отдельный домен `a11y` для компонента vnc **не заводится** (см. [use-cases/README.md](../use-cases/README.md)); общие требования доступности и WCAG MVP фиксируются как нефункциональные требования (NFR) в [nonfun-req/](../nonfun-req/README.md), а сценарии для пользователей вспомогательных технологий оформляются внутри `US-local.tray.*`.
