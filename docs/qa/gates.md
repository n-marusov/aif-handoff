# Гейты AI Factory — методология и каталог (AIF Handoff: система автономного управления задачами)

> Назначение: определить принципы и каталог гейтов AI Factory для LLM-генерации артефактов спецификации и для проверки достижения требований системы кодом. Гейты превращают генерацию артефактов из «ускоренного гадания» в управляемый процесс с измеримыми проверками на каждой стадии жизненного цикла артефакта, а реализацию требований — из декларации в подтверждённое тестами достижение.
> Методологическая база: матрица программирования качества (5 факторов × 4 этапа ЖЦ, `README.md` §2.4, §5.1), принципы контроля качества `README.md` §3, каталог фитнес-функций `.ai-factory/references/fitness-functions.md` (метрики + автоматизация + пороги = гейт).

---

Примечание о требованиях: каталог `fun-req/` создан: под «функциональным требованием (FR)» понимается требование `REQ-FR-*` (`fun-req/`) и в текущей форме — функция **HF1–HF12** (`vision.md` §2.2), прецедент `UC-*` (`use-cases/`) или бизнес-правило `BR-*`. Трассировка FR → тест ведётся штатно.

## 2. Модель: артефакты, LLM-контур, гейты

- **Артефакт** — единица спецификации с владельцем, схемой идентификаторов и шаблоном (определяется README каталога). Артефакт проходит стадии жизненного цикла (раздел 3).
- **LLM-контур** — агенты AI Factory, которые генерируют, редактируют и проверяют артефакты. Гейты применяются **внутри** контура (shift-left) и **снаружи** (CI, ревью).
- **Гейт** — проверка с измеримым результатом (`pass`/`fail`/`warn`), которая блокирует переход артефакта на следующую стадию. Гейт ≠ галочка: результат подтверждается артефактом проверки (отчёт, JSON, ревью-комментарий).
- **Владелец артефакта** — роль, принимающая решения по артефакту (критерии приёмки, приоритеты, TBD) и утверждающая его.
- **FR (функциональное требование)** — требование с критериями приёмки (`REQ-FR-*` из каталога `fun-req/`; в текущем контуре также функция HF/UC/BR с критериями `vision.md` §1.4 и DoD), которое после спецификации (`live`) переходит в реализацию: задача агенту → код → подтверждение тестами. Достижение FR подтверждается гейтами класса FG (раздел 6.4); FR без теста на критерии приёмки — «задекларировано», а не «реализовано».
- **Архитектурные артефакты** — C4-модель (`c4/`: контекст, контейнер, deployment; компоненты — целевое состояние) и архитектурные решения (`adr/` — `ADR-*.md`). Они задают ожидаемую структуру системы: расхождение реализации с диаграммой (изменённый/добавленный маршрут API, новое WS-событие, отсутствующий компонент) — дефект, который ловят гейты класса AG (раздел 6.5) (`README.md` §4.2).

## 3. Жизненный цикл артефакта и точки гейтинга

```
 draft ──G1──▶ validated ──G2──▶ reviewed ──G3──▶ approved ──▶ live
 (гене-   детермини-   LLM-проверки   ручное    утверждён,    (master,
 рация)   рованные     (скиллы-       ревью     готов к       источник
           скрипты/CI   аудиты)       человеком  merge        правды)
                                                              │
                                                    deprecated / archived
                                                    (вывод из эксплуатации)
```

| Стадия       | Вход                  | Гейты на выходе                                         | Результат                                                |
| ------------ | --------------------- | ------------------------------------------------------- | -------------------------------------------------------- |
| `draft`      | Задача/план/идея      | G1 (обязательный минимум: FMT, ID, LINK, DUP)           | Черновик с корректной структурой и ссылками              |
| `validated`  | Черновик              | G1 полный набор по типу артефакта (раздел 7)            | Артефакт соответствует шаблону, схеме ID и трассировке   |
| `reviewed`   | Валидированный        | G2 (CONSIST, QMATRIX, DEF, FF, QA, SEC, REVIEW по типу) | Подтверждена непротиворечивость и полнота                |
| `approved`   | Отревьюенный          | G3 (OWNER, ARCH, QA, APPROVE по типу)                   | Решения человеком приняты, waiver-ы зафиксированы        |
| `live`       | Утверждённый          | merge в `master`, CI-гейты                              | Артефакт становится источником для последующей генерации |
| `deprecated` | Вывод из эксплуатации | G1-LINK (регресс ссылок), запись замены                 | Нет «битых» ссылок; замена зафиксирована                 |

Правило: артефакт **не переходит** на следующую стадию, пока не пройдены все гейты текущей. Пропуск гейта — только по процедуре исключения (раздел 9).

Жизненный цикл требования не заканчивается на `live`: спецификация переходит в реализацию, и достижение подтверждается гейтами FG:

```
 live (спецификация требования: HF/UC/BR/FR, критерии приёмки)
   │
   ▼
 Реализация (задача агенту, aif-implement)
   │
   ▼
 FG-гейты достижения требования (локально у агента + CI)
   ├─ FG-BUILD — код собирается
   ├─ FG-UNIT — модульные тесты (локальные регрессионные) проходят
   ├─ FG-REGRESSION — существующий набор тестов не сломан
   ├─ FG-TEST — критерии приёмки покрыты автоматическим тестом
   ├─ FG-TRACE — требование ↔ тест: двухсторонняя трассировка, нет «сиротских» тестов
   ├─ FG-TEST-QUALITY — тесты верифицированы: детерминизм, нет тривиальных/«флаки»
   ├─ FG-MUTATION — мутационное тестирование критичных пакетов
   └─ FG-VERIFY — верификация против плана (aif-verify)
   │
   ▼
 AG-гейты — архитектурные проверки (локально + CI)
   ├─ AG-C4 / AG-ADR — соответствие C4-модели и архитектурным решениям
   ├─ AG-CYCLES / AG-LAYERS / AG-BOUNDARIES — структура и границы пакетов
   ├─ AG-CONTRACTS — контракты `docs/contracts/` (breaking changes)
   └─ AG-DEPS / AG-STRUCT — зависимости и структурные метрики
   │
   ▼
 Задача принята (Definition of Done) → CI (см. README.md §8) → merge
```

**Правило приёмки:** задача от агента принимается, **только если код собирается (`FG-BUILD`) и проходят модульные тесты — локальные регрессионные (`FG-UNIT`)**. Этот минимальный блокер обязателен независимо от остальных результатов; `FG-BUILD` и `FG-UNIT` не подлежат waiver (раздел 9).

## 4. Принципы гейтов LLM-генерации

1. **Измеримость.** Каждый гейт — бинарный критерий (`pass`/`fail`/`warn`) с детерминированным алгоритмом проверки или обоснованным заключением. «Проверено вручную» без измеримого результата гейтом не является (`README.md` §3, принцип 12).
2. **Автоматизация по умолчанию.** Детерминированные проверки (G1) — скриптами в CI и в агенте; LLM-проверки (G2) — только там, где нет детерминированного алгоритма; ручные (G3) — только решения человека. Метрика без регулярного автоматического применения с порогом — не гейт, а отчёт (`fitness-functions.md`, Best Practices 3).
3. **Shift-left.** Гейты применяются в момент генерации, а не только при ревью: агент обязан прогнать G1 до выдачи результата (`README.md` §3, принцип 10).
4. **Гейт на выходе каждой стадии.** Переход `draft → validated → reviewed → approved → live` блокируется непройденными гейтами текущей стадии.
5. **Трассируемость.** Артефакт, разрывающий цепочку `vision (HF1–HF12) → UC/BR → тест`, не проходит `G1-TRACE`; нарушение иерархии — дефект, а не стилистика.
6. **Детерминизм.** Одинаковый вход → одинаковый результат гейта. «Флаки»-гейт хуже отсутствующего: он обесценивает сигнал (`README.md` §3, принцип 8).
7. **Полнота по жизненному циклу.** Набор гейтов закрывает все ячейки матрицы программирования качества процесса генерации (раздел 8); концентрация гейтов только на «Функции × Генерация» — перекос, оставляющий вне контроля сопровождение и вывод из эксплуатации артефактов.
8. **Исключения фиксируются.** Гейт может быть пропущен только по процедуре waiver: запись в `open-questions.md` (риск, владелец, срок; артефакт запланирован по RULES.md). Молчаливый пропуск — дефект процесса.
9. **Гейт подтверждается артефактом проверки.** Отчёт, `aif-gate-result` JSON, комментарий ревью. Без подтверждения гейт не засчитывается.
10. **Критичность определяет глубину.** Артефакты и пакеты P0-областей системы (автомат стадий задачи, транзакционные переходы и владение задачей, аудит-трейл, аутентификация/CSRF, runtime-лимиты, изоляция worktree, резолюция runtime-профилей) проходят полный набор гейтов; P2 — по решению владельца (`README.md` §3, принцип 4).
11. **Достижение требования подтверждается тестом.** Требование считается достигнутым, только если его критерии приёмки покрыты автоматическим тестом (минимум unit-уровень). Реализация без теста — «задекларировано», а не «реализовано».
12. **Минимальный блокер приёмки задачи.** Задача от агента принимается, только если код собирается (`FG-BUILD`) и проходят модульные тесты — локальные регрессионные (`FG-UNIT`). Эти два гейта не подлежат waiver.
13. **Локальный прогон обязателен.** Гейты FG исполняются агентом локально до выдачи результата (shift-left); CI — повторный контроль, а не замена локального прогона.
14. **Архитектура — объект проверки.** Реализация сверяется с C4-моделью автоматически (класс AG): расхождение реализации с диаграммой (новый маршрут API, новое WS-событие, отсутствующий компонент) — дефект, а не стилистика (`README.md` §4.2). AG исполняются до приёмки задачи, наравне с FG.
15. **Тесты — объект контроля, а не только инструмент.** Качество тестов проверяется тремя уровнями: верификация (`FG-TEST-QUALITY` — детерминизм, отсутствие тривиальных/always-pass/`skip`-заглушек), трассировка к требованиям (`FG-TRACE` — двухсторонняя связь требование ↔ тест, нет «сиротских» тестов) и мутационное тестирование (`FG-MUTATION` — тест убивает мутации в критичных пакетах). Тест, который не может упасть, — не тест.

## 5. Классификация гейтов

| Класс  | Тип                                      | Результат                          | Кто выполняет                                    | Когда                                       |
| ------ | ---------------------------------------- | ---------------------------------- | ------------------------------------------------ | ------------------------------------------- |
| **G1** | Детерминированные автоматические         | `pass`/`fail`                      | Скрипты, CI, агент (shift-left)                  | В момент генерации и при merge              |
| **G2** | LLM-проверки (аудиты)                    | `pass`/`warn`/`fail` + обоснование | Скиллы AI Factory, кросс-ревью свежим контекстом | После валидации, перед ручным ревью         |
| **G3** | Ручные ревью                             | `approve`/`reject`                 | Владелец, архитектор, QA, PO/PM                  | Перед утверждением и merge                  |
| **FG** | Детерминированные, достижение требований | `pass`/`fail`                      | Агент (локально, shift-left), CI                 | При завершении задачи реализации требования |
| **AG** | Детерминированные, архитектурные         | `pass`/`fail`                      | Агент (локально), CI, интеграционные             | При завершении задачи реализации требования |

G1 ловит нарушения формы (структура, ID, ссылки, формат), G2 — нарушения содержания (противоречия, полнота, измеримость, галлюцинации), G3 — решения, которые не автоматизируются (критерии приёмки, приоритеты, допущения).

**FG (FR Gates)** — гейты достижения функциональных требований: исполняются агентом локально при завершении задачи и подтверждаются в CI (см. `README.md` §8). FG проверяют не форму артефакта, а факт реализации требования: сборку, модульные тесты, регресс, покрытие критериев приёмки тестами.

**AG (Architecture Gates)** — архитектурные гейты: проверяют соответствие реализации C4-модели, границы пакетов, циклы зависимостей, контракты. AG исполняются до приёмки задачи (наравне с FG) и повторяются в CI.

### 6.2. G2 — LLM-проверки (аудиты скиллами)

### 6.4. FG — гейты достижения требований

Условие приёмки задачи от агента (Definition of Done). **Минимальный блокер — `FG-BUILD` + `FG-UNIT`** (обязателен для любой задачи); полный набор — по приоритету требования: P0/P1 — обязателен, P2 — по решению владельца. Локальный прогон у агента обязателен до выдачи результата; CI — повторный контроль.

| ID                | Гейт                        | Что проверяет                                                                                                                                                                                                                                                       | Где исполняется                                                                            | Статус                                                                                                                                                            |
| ----------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FG-BUILD`        | Сборка                      | Код собирается: `turbo build` / `npm run build` (tsc + vite) без ошибок компиляции и типов                                                                                                                                                                          | Локально у агента + CI                                                                     | ✅ Сборка в CI (`build.yml`); локальный прогон — обязателен                                                                                                       |
| `FG-UNIT`         | Модульные тесты             | Локальные регрессионные тесты проходят: `vitest run` (turbo test) по затронутым пакетам                                                                                                                                                                             | Локально у агента + CI                                                                     | ✅ Тесты во всех пакетах (`packages/*/src/__tests__`); открытые KI — `known-issues.md`; быстрый гейт `make gate-fast` (fail-fast), полный прогон — `make test`    |
| `FG-REGRESSION`   | Регресс                     | Существующий набор тестов смежных пакетов не сломан; нет регрессий в зависимых требованиях                                                                                                                                                                          | Локально + CI                                                                              | ✅ Покрывается `turbo test` / `tests.yml` (полный прогон); отдельный регресс-прогон перед релизом — целевое                                                       |
| `FG-TEST`         | Критерии приёмки            | Каждый критерий приёмки требования покрыт автоматическим тестом (минимум unit-уровень); негативные сценарии включены                                                                                                                                                | Агент (пишет тест) + ревью                                                                 | 🟡 Правило вводится; тест на требование обязателен                                                                                                                |
| `FG-TRACE`        | Трассируемость              | Двухсторонняя связь требование ↔ тест: каждый критерий покрыт тестом (forward); каждый тест трассируется к требованию — нет «сиротских» тестов (backward); сверка с матрицей качества (`README.md` §5)                                                              | Агент + скрипт (план)                                                                      | 🔴 План                                                                                                                                                           |

| `FG-MUTATION`     | Мутационное тестирование    | Мутации вносятся в критичные модули (автомат стадий `stateMachine.ts`, переходы/handoff `taskTransitions.ts`/`taskOwnership.ts`, аудит, auth/CSRF, runtime-лимиты, резолюция профилей, изоляция worktree); выжившие мутации = пробел в тестах; mutation score ≥ 80% | Локально (критичные модули) + CI (ночной/релизный прогон)                                  | 🟡 Инструмент подключён (`@stryker-mutator/core`, `npm run mutation`); порог 80% и CI-прогон — целевое состояние                                                  |
| `FG-VERIFY`       | Верификация против плана    | Реализация закрывает задачи плана; нет дрейфа план ↔ код; задача не «закрыта галочкой»                                                                                                                                                                              | Скилл `aif-verify`                                                                         | ✅ Есть (strict mode)                                                                                                                                             |
| `FG-COVERAGE`     | Порог покрытия кода тестами | Покрытие кода тестами (утверждения/ветки, `@vitest/coverage-v8`) по пакетам unit-скоупа ≥ **70%** (lines/functions/branches/statements); enforced, а не отчёт                                                                                                       | Локально — отчёт (`make coverage`); CI (`tests.yml` — `npm run coverage`, fail при пороге) | ✅ Порог 70% на пакет зафиксирован в `vitest.config.ts` и enforced в CI; открытые пробелы — `known-issues.md` (`schema.ts` 0% в shared, выборочный include в web) |

Порядок внедрения контроля качества тестов: 1) `FG-TEST-QUALITY` (линтеры тестов, анти-«флаки») → 2) `FG-TRACE` (скрипт-сверка требование ↔ тест) → 3) `FG-MUTATION` (мутационный прогон критичных пакетов, порог 80%).

> Порог `FG-COVERAGE` (70% на пакет) локален для репозитория AIF Handoff и enforce-ится через `vitest.config.ts` thresholds каждого пакета (команда покрытия с порогом — `make coverage` / CI `tests.yml`). Известные пробелы покрытия и флейки фиксируются в `docs/known-issues.md`; при вводе fail-проверки порог калибруется по пакетам с владельцем.

## 8. Связь с матрицей программирования качества

Матрица программирования качества (`README.md` §2.4) применена к **процессу генерации артефактов**: факторы обусловленности × этапы жизненного цикла артефакта. Каждая ячейка закрывается минимум одним гейтом из каталога; пустая или неизмеримая ячейка — «свободный параметр» процесса и фиксируется в `open-questions.md` (запланирован по RULES.md).

| Фактор \ Этап ЖЦ артефакта                                                  | 1. Генерация (draft)                                                                                                                                                       | 2. Валидация и использование (validated/reviewed)           | 3. Сопровождение (актуализация)                                         | 4. Вывод из эксплуатации (deprecated)   |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------- |
| **1. Среда** (контекст генерации: глоссарий, референсы, язык, регуляторика) | `G1-GLOSS`, `G1-FMT` (язык); контекст из актуальных `live`-артефактов                                                                                                      | `G2-CONSIST` (согласованность с референсами); `G1-LINK`     | `G1-LINK` (ссылки на актуальные источники); `G2-CONSIST` при изменениях | Пометка замены; ссылки на преемника     |
| **2. | **3. | **5. Пояснения:

- Гейты — инструмент закрытия ячеек матрицы для процесса генерации: **каждый гейт измерим** (принцип 1), поэтому ячейка считается закрытой, только если проверка даёт `pass`/`fail`/`warn` с обоснованием.
- FG-гейты закрывают ячейки этапа 1 (Генерация/Реализация) для кода: критерии приёмки, заданные при спецификации требования (`G1-METRIC`), превращаются в тесты (`FG-TEST`) и подтверждаются сборкой и прогоном (`FG-BUILD`, `FG-UNIT`).
- Контроль качества тестов (мета-уровень) закрывает ячейку «Аварии × Реализация»: `FG-TEST-QUALITY` (тест не тривиален и не «флакает»), `FG-MUTATION` (тест убивает мутации — реально ловит дефекты), `FG-TRACE` (тест связан с требованием — нет «сирот»). Покрытие утверждений (`FG-COVERAGE`) показывает широту, mutation score — глубину тестов.
- AG-гейты закрывают те же ячейки для архитектуры: C4 задаёт ожидаемую структуру, а `AG-C4`/`AG-CYCLES`/`AG-LAYERS`/`AG-BOUNDARIES`/`AG-CONTRACTS` подтверждают, что реализация не разошлась с ней (структурные фитнес-функции, `fitness-functions.md` «Связанность и структура»).
- Концентрация гейтов только в ячейке «Функции × Генерация» — перекос («ловушка 3.2» из `README.md` §2.4): вне контроля остаются актуализация артефактов и их вывод из эксплуатации. Поэтому `G1-LINK`-регресс и `G1-TBD` обязательны для всех типов артефактов.
- Метрики процесса (доля артефактов, прошедших гейты; доля waiver-ов; время от draft до live) — кандидаты на continual-фитнес-функции процесса (`fitness-functions.md`, категория «Pipeline & Process»).

## 9. Политика исключений (waiver) и TBD

1. **Waiver** — официальный пропуск гейта. Оформляется записью в `open-questions.md` (артефакт запланирован по RULES.md): ID исключения, пропущенный гейт, риск, владелец, срок закрытия.
2. Waiver допустим только для `G2`/`G3`; для `G1` — только на стадии `draft` (черновик может быть неполным, но обязан иметь корректные ID и ссылки, иначе дефекты тиражируются).
3. **TBD-флаг** — пробел в артефакте. Артефакт с `[TBD-xx]` не переходит в `live`, пока TBD не закрыт или не зафиксирован как waiver с владельцем и сроком (например, метрики целей в `vision.md` §1.4).
4. Молчаливый пропуск гейта (без waiver) — дефект процесса, фиксируется в `qa/` и разбирается в ревью процесса.
5. **FG-гейты**: `FG-BUILD` и `FG-UNIT` — минимальный блокер приёмки задачи, waiver не подлежат (принцип 12). `FG-TEST`, `FG-TRACE`, `FG-COVERAGE` — waiver допустим только с владельцем и сроком (например, тест на критерии приёмки требования отложен на одну итерацию с записью в `open-questions.md`).
6. **Контроль качества тестов**: `FG-TEST-QUALITY` — waiver не подлежит (тривиальный тест хуже отсутствующего: он создаёт ложную уверенность). `FG-MUTATION` — waiver допустим для некритичных пакетов; для критичных (автомат стадий, переходы/handoff, аудит, auth/CSRF, runtime-лимиты, резолюция профилей, изоляция worktree) — обязателен, mutation score ≥ 80%; снижение порога — только с QA-инженером и владельцем (запись в `open-questions.md`).
7. **AG-гейты**: waiver допустим только с владельцем-архитектором и сроком; `AG-CONTRACTS` и `AG-CYCLES` — без waiver (тиражируют дефекты в контракты и связанность пакетов).

## 10. Порядок применения в AI Factory-контуре

```
Генерация (агент)
  ├─ shift-left: G1-FMT, G1-ID, G1-LINK, G1-DUP — до выдачи результата
  ├─ G1 полный набор по типу артефакта (раздел 7)
  └─ aif-gate-result (JSON) прикладывается к результату
        │
        ▼
LLM-проверки (G2)
  ├─ G2-RULES (aif-rules-check) — обязателен для изменённых файлов
  ├─ G2-COMMENTS — качество комментариев в изменённых *.ts/*.tsx-файлах (доменный смысл, метки трассировки)
  ├─ G2-CONSIST / G2-QMATRIX / G2-DEF / G2-FF / G2-QA / G2-SEC / G2-REVIEW — по типу
  └─ Каждый гейт: verdict + обоснование; fail → возврат на генерацию
        │
        ▼
Ручные ревью (G3)
  ├─ G3-OWNER / G3-ARCH / G3-QA — по типу артефакта
  ├─ G3-APPROVE — перед merge в master
  └─ reject → возврат; waiver → запись в open-questions.md
        │
        ▼
live (master)
  └─ CI: G1-C4, G1-детерминированные скрипты, aif-gate-result из отчётов

Реализация требования (задача агенту, из плана)
  ├─ FG-BUILD: turbo build / npm run build — до выдачи результата (shift-left)
  ├─ FG-UNIT: vitest run / npm test — локальные регрессионные тесты
  ├─ FG-TEST: тест на критерии приёмки (минимум unit) + FG-TRACE (требование ↔ тест)
  ├─ FG-TEST-QUALITY: тесты верифицированы — детерминизм, нет тривиальных/always-pass
  ├─ FG-MUTATION: мутационный прогон критичных пакетов (локально) — тест убивает мутации
  ├─ FG-REGRESSION: существующий набор тестов не сломан (turbo test)
  ├─ FG-VERIFY: aif-verify (strict mode) — задача закрыта только при прохождении
  ├─ AG-C4 / AG-ADR / AG-CYCLES / AG-LAYERS / AG-BOUNDARIES / AG-CONTRACTS — архитектурные проверки
  └─ результат: отчёт FG + AG + aif-gate-result; без FG-BUILD + FG-UNIT задача не принимается
        │
        ▼
CI (см. README.md §8): lint, unit, coverage (70%), build, контракты — повторный контроль
```

Порядок исполнения: агент не завершает задачу, пока не пройдены гейты своей стадии; нарушение фиксируется как дефект процесса. Связка «артефакт → гейты → отчёты» — кандидат на проверку автоматической связкой «задача → MR» (GitHub Actions).
