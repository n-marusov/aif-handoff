# ADR-DES.STACK.modular-monolith-adoption

**Статус:** ПРИНЯТО
**Дата:** 2026-09-14
**Контекст:** Проект AIF Handoff с самого начала проектировался как система с чёткими доменными границами: слой данных, API, UI, оркестрация агентов. На момент принятия решения команда небольшая, развёртывание единое — микросервисы создали бы избыточную операционную нагрузку. При этом без формальных модульных границ разнонаправленный код (Schema ↔ HTTP ↔ React ↔ SQL) начал бы смешиваться в одном пакете.

**Требование-источник:** `vision.md` §1 (бизнес-требования), `.ai-factory/ARCHITECTURE.md`, `docs/architecture.md`

**Решение:** Использовать Modular Monolith, реализованный через Turborepo workspaces. Семь независимых пакетов (`shared`, `runtime`, `data`, `api`, `web`, `agent`, `mcp`) — каждый со своей сборкой, тестами и зависимостями — развёртываются и работают как единая система. Turborepo обеспечивает кеширование сборок, параллельный запуск задач и единую конфигурацию через `turbo.json`.

**Рассмотренные альтернативы:**

- **Микросервисы** — каждый пакет как отдельный сервис с HTTP/gRPC API. Отвергнуто: команда мала, операционные затраты (CI/CD, мониторинг, оркестрация) неоправданны, latency при внутрипроцессных вызовах отсутствует.
- **Единый монолит** — один пакет без модульных границ. Отвергнуто: потеря доменных границ, coupling разнородного кода, сложность тестирования изолированных слоёв.

**Последствия:**

- **Положительные:** чёткие контракты между пакетами (`exports` в package.json), параллельная сборка, изолированное тестирование.
- **Отрицательные:** риск нарушения dependency rules при отсутствии бдительности; все пакеты разделяют один процесс, ошибка в одном может уронить всю систему.
- **Смягчение:** явные dependency rules (см. ARCHITECTURE.md), линт-проверки, запрет кросс-пакетных глубоких импортов. Все межпакетные вызовы — через public API (`@aif/*`), а `web → api` — только через HTTP/WS.
