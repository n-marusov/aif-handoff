# ADR-IMPL.DATA.migration-append-only

**Статус:** ПРИНЯТО
**Дата:** 2026-09-14
**Контекст:** База данных SQLite обновляется через миграции, определённые в `packages/data/src/db.ts` (адрес после clean-architecture рефакторинга; ранее `packages/shared/src/db.ts`). Поскольку экземпляры БД существуют на разных машинах разработчиков и в production, каждая миграция должна быть иденпотентно применяема к любому состоянию схемы. При разработке в параллельных ветках git неизбежны коллизии номеров миграций — если две ветки закоммитили миграцию под номером 15, при слиянии одна перезапишет другую, и БД пользователей, уже применивших 15, пропустит новую.

**Требование-источник:** `RULES.md` (пункт «Migration version numbers are append-only»), `docs/architecture.md` §Database

**Решение:** Миграционные версии — append-only: никогда не переименовывать и не редактировать SQL уже слитой миграции. В случае коллизии на одну и ту же версию при merge — первая слитая ветка сохраняет свой номер, вторая получает следующий свободный номер. Массив `MIGRATIONS` обрабатывается последовательно; функция `runMigrations` проверяет `PRAGMA user_version` и применяет только те миграции, чей номер больше текущей версии. Ошибки вроде `duplicate column` при повторном применении игнорируются через `isIgnorableMigrationError` (проверка SQLite error code).

**Рассмотренные альтернативы:**

- **Нумерация по git SHA** — версия миграции = хеш коммита. Отвергнуто: хеши не упорядочены, нельзя определить «следующую» миграцию; `PRAGMA user_version` — integer.
- **Timestamp-based версии** — версия = ISO-метка времени. Отвергнуто: при часовых поясах и параллельных коммитах коллизии вероятны; `user_version` требует integer.
- **Нумерация PR/MR номером** — версия = номер PR. Отвергнуто: PR недетерминирован для нумерации на этапе разработки.

**Последствия:**

- **Положительные:** нулевой риск расхождения схемы между кодом и БД пользователей; коллизии разрешаются автоматически на merge (добавить новую запись с последним номером); `PRAGMA user_version` — простой, надёжный счётчик.
- **Отрицательные:** номера миграций не отражают логический порядок (версия 15 может быть создана после версии 17); recovery-миграции (ALTER TABLE ADD COLUMN для БД, пропустивших колонку) добавляют новый номер с DDL, который уже был в предыдущей — но `isIgnorableMigrationError` делает это безопасным.
- **Смягчение:** документация в RULES.md и AGENTS.md с явным предупреждением; при конфликте merge — всегда смещать номер проигравшей ветки, никогда не редактировать существующее.
