# ADR-DES.SECURITY.auth-session-model

**Статус:** ПРИНЯТО
**Дата:** 2026-09-14
**Контекст:** AIF Handoff предоставляет веб-интерфейс (Kanban, чат, администрирование) и HTTP API для MCP-клиентов. Неавторизованный доступ к API позволяет любому участнику сети создавать/удалять задачи и управлять проектом. API должен различать анонимный доступ, сессионный (браузер) и машинный (MCP-токен). Participants Mode добавляет ролевой контроль: администратор, участник, наблюдатель — с разными разрешёнными действиями.

**Требование-источник:** `vision.md` §2.5 (безопасность),docs/architecture.md §Participants Ownership

**Решение:** Трёхуровневая модель аутентификации:

1. **Basic Auth** — глобальный `API_USER`/`API_PASSWORD` для доступа к API вне браузера (curl, тесты). Legacy-уровень, отключаемый через `AIF_API_KEY=none`.
2. **Session-токены + CSRF** — браузер аутентифицируется через opaque session cookie. CSRF-токен, привязанный к сессии, защищает mutation-запросы. WebSocket-апгрейд проходит ту же проверку сессии и Origin-заголовка. Сессии хранятся в SQLite через `packages/data/src/authSessions.ts`.
3. **MCP Bearer Token** — HTTP MCP использует отдельный bearer-токен (`MCP_API_KEY`) без сессий. MCP не может мутировать ownership задач.
4. **Participants Mode (optional)** — включает ролевую модель: при `PARTICIPANTS_MODE_ENABLED=true` добавляются проверки прав на каждое действие. Роли: `admin` (полный доступ), `member` (стандартные действия), `observer` (только чтение). Каждое действие имеет разрешённые роли, и API возвращает 403 при нехватке прав.

**Рассмотренные альтернативы:**

- **JWT-only** — только JWT-токены для всех клиентов. Отвергнуто: JWT требует управления ключами подписи, сложнее для локального dev-сценария; Basic Auth проще для машинного доступа.
- **OAuth 2.0 / OIDC** — внешний identity provider. Отвергнуто: избыточно для single-user/multi-user сцены; зависимость от внешнего сервиса (Keycloak, Auth0) для проекта, где развёртывание должно быть простым (`docker compose up`).
- **Отсутствие аутентификации (public API)** — минимальная защита через reverse-proxy (Angie). Отвергнуто: встроенная сессионная аутентификация — минимальная база; reverse-proxy не различает пользователей для Participants Mode.

**Последствия:**

- **Положительные:** локальный dev — без настройки external auth; CSRF-защита встроена в Middleware; Participants Mode добавляет ролевой контроль без смены архитектуры.
- **Отрицательные:** Basic Auth — legacy-уровень, менее безопасный (пароль в заголовке); сессии требуют таблиц в SQLite; RABC-правила участников — сложность, растущая с числом ролей и действий.
- **Смягчение:** Basic Auth может быть полностью отключён (`API_USER=none`); session-токены генерируются через crypto.randomUUID; CSRF сверяется через `x-csrf-token` header с солью сессии. Для future: OAuth-провайдер может быть добавлен как дополнительный транспорт без изменения модели.
