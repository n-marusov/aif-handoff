## E2E GUI: в UI нет композера комментариев к задаче, US ожидает его

- **Статус:** открыто (2026-09-20), расхождение требования ↔ реализация
- **Симптом:** сценарий `US-dashboard.detail.view-task-details` («Пользователь добавляет комментарий
  к задаче») предполагает ввод комментария в UI детального просмотра. В текущей реализации вкладка
  `Comments` в `TaskDetail` — read-only (`TaskComments` рендерит только ленту); `POST
/tasks/:id/comments` вызывается лишь из API-клиента (агентские комментарии, диалоги репланов) и
  недоступен через пользовательский интерфейс деталей задачи.
- **Причина:** реализация не предоставляет UI-композер комментариев; US/UC опережают реализацию
  (to-do на уровне GUI-контура).
- **Действие:** E2E GUI-проверка `L-02` ограничена отображением ленты: комментарий, созданный через
  реальный API (`POST /tasks/:id/comments`), появляется во вкладке Comments. Сценарий «добавить
  комментарий через UI» не имитируется; при появлении композера расширить спект.

## E2E GUI: US-сценарий списка колонок не совпадает с набором статусов приложения

- **Статус:** открыто (2026-09-20), расхождение требования ↔ реализация
- **Симптом:** `US-dashboard.board.view-kanban-columns` перечисляет 11 колонок стадий, включая
  «Plan Ready» и «Plan Review». Реальный Kanban рендерит 10 колонок по `STATUS_CONFIG`
  (`packages/shared/src/constants.ts`): Backlog, Planning, Improve, **Plan Review**, Implementing,
  Verify, Review, Blocked, Done, Accepted. Колонки «Plan Ready» в приложении нет.
- **Причина:** статус `plan_review` в реализации называется «Plan Review»; отдельной стадии
  «Plan Ready» не существует (гейт mark_plan_ready — событие, а не стадия). US описывает целевой
  контур с большей детализацией.
- **Действие:** E2E GUI-проверка L-01 опирается на реальные подписи `STATUS_CONFIG`. При
  расхождении US/реализации расширить: либо актуализировать US, либо добавить стадию. Пока
  расхождение зафиксировано здесь и не «чинится» в тесте.

## E2E GUI: сценарии auth/roles (L-08, L-06) невыполнимы на стенде с `PARTICIPANTS_MODE_ENABLED=false`

- **Статус:** открыто (2026-09-20), внешнее ограничение стенда, не связано с кодом
- **Симптом:** E2E GUI-сценарии `L-08` (`UC-auth.registration.sign-up-participant` — регистрация/вход)
  и `L-06` (`UC-auth.roles.assign-participant-role` — роли участников) не могут быть выполнены на
  dev-стенде: `PARTICIPANTS_MODE_ENABLED=false` в `.env` стенда. `/auth/session` возвращает
  `participantsModeEnabled:false`, `/participants` — `participants_mode_disabled`, UI не рендерит
  LoginPage (`App.tsx`: `auth.session.participantsModeEnabled && !authenticated → LoginPage`),
  диалог управления участниками недоступен.
- **Причина (окружение):** US-сценарии требуют включённого режима участников; на стенде он выключен
  намеренно (dev-режим без аутентификации). По правилу «не менять ни код, ни сценарий» тесты против
  реального стека не пишутся под mock, а сценарий не «чинится» под окружение.
- **Действие:** при включении `PARTICIPANTS_MODE_ENABLED=true` на стенде (и перезапуске dev-стека)
  реализовать L-08/L-06 как реальные E2E GUI-спекты (регистрация первого admin, вход, смена роли);
  пока флаг выключен — спекты запускаются в режиме проверки выключенного состояния (или явный
  skip с причиной), без имитации прохождения.

## `schema.ts` в `@aif/shared`: 0% покрытия в собственном отчёте shared после переноса сьютов в data

- **Статус:** принято; покрытие пакета держится выше 70% (79.9/78.5/77.0/75.0)

- **Действие:** если понадобится «честное» покрытие схемы в shared — добавить лёгкий контрактный тест

## E2E perf-гейт (`ai:perf`) капризен на локальных машинах (Windows)

- **Статус:** открыто (не связано с clean-architecture рефакторингом; web/ не менялся)
- **Симптом:** `npm run ai:perf` (Playwright E2E против живых dev-серверов, `packages/web/e2e/perf/*`) иногда падает на бюджетах: `dashboard-load` («renders kanban shell within LCP/DOM-ready budgets») и `chat-sessions-endpoint` («cold and warm reads stay under budgets»). Типичная ошибка — `waitForSelector` не находит `Backlog|Planning|Implementing|Projects overview|No projects yet` в 30s или `domContentLoadedMs/LCP` превышают `PERF_BUDGETS`. При этом на повторном прогоне тот же/другой spec может пройти — набор падающих тестов между прогонами меняется.
- **Причина:** измерение времени против cold-start dev-серверов на локальном железе: пустая база perf-окружения, прогретость Vite/API, загрузка машины, кеша браузера. Бюджеты жёсткие (LCP/DOM-ready), а budget-тесты недетерминированны по определению.
- **Проверка:** перезапустить `npm run perf --workspace=@aif/web`; прогон обычно проходит целиком на следующем запуске.
- **Действие:** не трактовать красный perf-гейт как поломку `web/` кода; для CI рассматривать soft-fail на бюджетные прогоны или усреднение по нескольким запускам. В детерминированном гейте `ai:validate` (план feature/fix-known-issues-followups) `ai:perf`/`ai:load` не блокирующие — отчёт отдельный, со ссылкой на эту запись.

## Общие операции задач живут в `@aif/data`, а не в use-case фреймворке API

- **Статус:** принято (архитектурное решение Task 21, Variant A)
- **Симптом:** плановый «use cases as API, shared with MCP» невозможен буквально: `@aif/mcp`
  разворачивается независимо от `@aif/api` (Docker-стадия mcp копирует только data/runtime/mcp;
  зависимости mcp по package.json — только `@aif/data` + `@aif/shared`). Импорт `@aif/api` из MCP
  утянул бы весь HTTP-сервер в рантайм MCP (hono, WebSocket, api-сервисы) + потребовал бы изменения
  Docker/turbo/coverage/eslint.
- **Причина:** Layer-модель проекта: application-операции, нужные нескольким доставкам, обязаны жить
  ниже обеих точек доставки. `@aif/data` уже содержит политические композиты (`handoffTaskExecution`,
  `transitionTaskStatus`, лимиты), поэтому «управляемые» операции задач добавлены туда
  (`packages/data/src/taskOperations.ts`): `createTaskManaged`, `updateTaskManaged`,
  `setTaskPlanContentManaged`, `validateProjectScopedRuntimeProfileSelections`.
- **Действие:** при добавлении новой общей операции задачи расширять `taskOperations.ts`, а не
  дублировать правило в api- и mcp-коде. API use-cases остаются оркестраторами (участковая
  авторизация, вложения, файлы плана); MCP-инструменты зовут те же операции напрямую.

## `pushPlan` (MCP) пишет план в поле задачи, а не в файл плана

- **Статус:** принято (сохранение контракта инструмента)
- **Симптом:** `handoff_push_plan` (MCP) записывает `plan` в колонку задачи
  (`setTaskPlanContentManaged` → `setTaskFields`), тогда как API `updateTaskPlan` пишет канонический
  файл плана (`.ai-factory/PLAN.md`) через `persistTaskPlanForTask`. До рефакторинга MCP делал те же
  `setTaskFields`; Task 21 не менял это поведение.
- **Причина:** push-plan доставляет план из внешней системы (Handoff) в поле, а не в файл; клиенты
  MCP рассчитывают на компактный ответ без файловых операций. Это осознанное расхождение двух
  контрактов записи плана.
- **Действие:** если требуется единый «источник правды» плана — синхронизировать pushPlan с
  файловым путём (как `updateTaskPlan`) и согласовать с MCP-клиентами, либо документировать поле vs
  файл как разные контракты.

## Usage-broadcast после Task 24 привязан к внедрённому реестру (consequence)

- **Статус:** предложение от /aif-review (Task 24; не блокирует)
- **Симптом:** субагентские фазы, исполняемые вне штатного entry point агента (например, будущие
  встраиваемые вызовы `executeSubagentQuery`), больше не рассылают `task:usage_updated`/лимитные
  broadcast, если не внедрён реестр с usage-sink'ом. Раньше subagentQuery поднимал свой собственный
  sink с `notifyRuntimeUsageRefresh`; после Task 24 уведомления об usage делает исключительно sink
  композиционного корня (`packages/agent/src/index.ts`) при `bootstrapRuntimeRegistry`.
- **Причина:** единый владелец порта (Task 24): реестр + `createDbUsageSink` создаются один раз в
  composition root и внедряются через `setRuntimeRegistry`; `subagentQuery` читает только
  `requireRuntimeRegistry()`. Для штатного пути это поведение-эквивалентно, но любой обходной запуск
  без инъекции молча теряет broadcast'и usage/лимитов.
- **Действие:** при добавлении новых точек запуска субагентов вне координатора — либо внедрять
  реестр с sink'ом явно, либо документировать отсутствие broadcast'ов как ожидаемое поведение.

## Done rework: доработка идёт через generic implementer, а не скилл `$aif-fix`

- **Статус:** открыто (2026-09-21), расхождение требования ↔ реализация
- **Симптом:** при `request_changes` из `done` (`done → implementing`, `reworkRequested=true`)
  стадия доработки запускает общий реализационный прогон (`runImplementer`,
  `packages/agent/src/subagents/implementer.ts`, слэш-команда `/aif-implement`) с
  REWORK-шапкой. ADR `ADR-IMPL.PROCESS.task-state-machine` и US
  `US-pipeline.stage.done-to-implementing-rework` требуют, чтобы в этом случае вызывался
  скилл `$aif-fix`: агент полагает задачу выполненной корректно (все формальные гейты —
  verify/review — пройдены), однако человек явно указывает, что реализация неправильна;
  скилл ориентирует исправление ровно на замечания человека, а не на «переделать заново».
- **Причина:** скилл `$aif-fix` (`.agents/skills/aif-fix/`) не подключён к стадии доработки
  coordinator-контура; implementer обрабатывает rework как специальный режим обычного
  прогона (rework-header, `latestReworkComment`, `blockingFindingsSnapshot`), но без
  фикс-направленного промпта скилла.
- **Действие:** подключить вызов скилла `$aif-fix` к стадии доработки из `done`
  (fix-направленный промпт с комментарием человека как первичным указанием); сохранить
  существующую REWORK-механику для review-loop; добавить тест, что промпт доработки из
  `done` адресует замечания человека, а не «всё готово» по пройденным гейтам.
- **Связанного:** фиксация сценария — `US-pipeline.stage.done-to-implementing-rework`;
  поведение перехода — `done → implementing` в `ADR-IMPL.PROCESS.task-state-machine`.

## Эволюция скиллов: `$aif-evolve` не запускается после накопления 5+ патчей `$aif-fix`

### Дефект D — фоновый шум в логах от legacy-проекта (`gitlab_prepare_fetch_failed` для `/home/www/vnc`)

   - `packages/agent/src/coordinator.ts` + `packages/agent/src/githubWorkflow.ts`/`gitlabWorkflow.ts`
   - логи `agent`: периодические fetch/auth ошибки для внешнего remote, не связанного с текущими e2e.
2. **Причина**
   - в e2e-стенде одновременно присутствуют тестовые и legacy-проекты; координатор
     обрабатывает оба набора и пишет ошибки вне test-scope.
3. **Классификация**
   - **Observability Scope Defect / Test Isolation Defect**.
4. **Статус: REFINE (2026-09-21)** — адресуется наблюдаемостью и изоляцией лог-scope:
   - трейс-корреляция (P2.1): `traceId`/`testId` в спектах и mapping-таблица в trace-matrix;
   - рекомендация: e2e-lane запускать координатор только по e2e-помеченным проектам
     (tracked как follow-up в final report «What remains»).

### Дефект E — `agent-notifier` 404 при broadcast после удаления задачи

1. **Локализация**
   - `packages/agent/src/notifier.ts` и связанный путь cleanup/remove task.
   - логи `agent`: 404 на broadcast для уже удалённой сущности.
2. **Причина**
   - гонка между удалением/cleanup и попыткой публикации события по уже недоступной задаче.
3. **Классификация**
   - **Concurrency / Eventual-Consistency Defect**.
4. **Статус: частично устранено 2026-09-21 (план «US + E2E Refactor», P1.3/политика слоёв)**
   - Покрытие broadcast-событий переведено на политику primary/secondary oracle-слоёв;
     E2E-сценарии более не полагаются на хрупкие order-догадки broadcast'ей.
   - Конкурентная гонка в notifier (idempotent broadcast c reason=`already_deleted`)
     остаётся follow-up на уровне agent-контура и требует отдельного плана.
