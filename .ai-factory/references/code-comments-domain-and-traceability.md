## Overview

Руководство по написанию комментариев в коде компонента **VNC** (`epc-vnc`). Два сквозных принципа:

1. **Комментарий передаёт смысл и поведение предметной области** (зачем, какое доменное правило и инвариант кодирует код), а не зеркалит строки кода (что делает каждая инструкция).
2. **Комментарий — носитель трассировки требований**: устойчивый идентификатор `REQ-FR-*` / `REQ-NFR-*` / `BR-*` / `VF*` / `UC-*` / доменного события в коде связывает реализацию с требованием и делает цепочку `Vision → UC → FR → ADR → COMP → TEST` проверяемой.

Комментарий — это объяснение, которое **нельзя выразить именем, типом или структурой кода**; всё остальное — шум. Код отвечает на вопрос «как», комментарий — на вопросы «почему», «какое правило», «какое исключение», «какой инвариант».

## Core Concepts

### Почему код ≠ документация, а комментарий ≠ пересказ

- Код читается построчно и показывает **механику**. Комментарий должен показывать **намерение и контракт**: что гарантирует функция, какое бизнес-правило соблюдает ветка, какое доменное событие порождает действие.
- Комментарий-пересказ удваивает стоимость изменений (правится в двух местах) и не добавляет информации: `i++ // увеличиваем i` бесполезен.
- Хороший тест на полезность: **удали комментарий — потеряется ли знание, которое нельзя восстановить из кода и имён?** Если нет — комментарий лишний.

### Доменная семантика (Ubiquitous Language)

- Компонент моделируется на языке предметной области из `specs/glossary.md`: *VNC-сессия, код доступа, репитер (VNC Repeater), кассовый узел, агент mdl, фреймбуфер, оверлей, готовое VNC-решение (из AC)*. Комментарий обязан использовать этот язык, а не изобретать синонимы (например, «тёмный экран» вместо «скрытие рабочего стола»).
- DDD-модель (`specs/domain/`) фиксирует **ограниченные контексты** (`vnc-access`, `vnc-session`, `vnc-configuration`), **агрегаты** (`VncServer`, `VncSession`, `VncClientSession`, `VncConfiguration`, `LogConfiguration`) и **инварианты**. Если код поддерживает инвариант агрегата — комментарий называет инвариант доменным языком.
- **Инвариант**: бизнес-правило, которое должно соблюдаться всегда (пример: «рабочий стол скрыт на время VNC-сессии и восстанавливается после» — инвариант контекста удалённого доступа). Комментарий у места enforcement (проверки/установки) фиксирует, *какой именно* инвариант и *почему* он здесь.

### Что может объяснять только комментарий

| Знание | Пример для VNC |
|---|---|
| Бизнес-правило / BR | «в режиме `auto` после завершения сессии отключением клиента код доступа ротируется» (`BR-action.access-code-rotated-after-session`) |
| Инвариант | «входящих портов нет — только исходящий туннель к репитеру» (`BR-integrity.no-inbound-ports`) |
| Намерение / цель операции | «маскировка пикселей оверлея перед отправкой VNC-клиенту» (`Options.CaptureHookProcess`) |
| Неочевидное ограничение протокола | «RFB VNCAuth: ключ DES всегда 8 байт» (`VNCPasswordKeyLenght`) |
| Причина выбора (почему так) | «Доработка для UltraVNC Repeater: заголовок 250 байт с префиксом ID:» |
| Платформенное различие | «на Windows не нужно: `WDA_EXCLUDEFROMCAPTURE` исключает оверлей из захвата» |
| Связь с требованием | «реализует `REQ-FR-remote.session.establish-rfb-session`, критерий 2» |

### Трассируемость требований в коде

- В проекте цепочка трассировки: **Vision (`VF1–VF7`) → UC → FR → ADR → COMP → TEST** (`specs/domain/README.md`). Требование → реализация прослеживается по устойчивым идентификаторам.
- **Направление ссылок одностороннее** (`.ai-factory/RULES.md`): артефакты требований (`specs/`) **не ссылаются на код** (пути, файлы, символы). Ссылка «код → требование» через комментарий-метку — единственный допустимый и достаточный механизм forward-трассировки.
- Метка в коде = **канонический ID требования** (не название файла, не ссылка-текст). ID стабилен, уникален и проверяем (`grep`-абелен), а текст требования живёт только в `specs/`.
- Схемы идентификаторов проекта (единый источник — README каталогов `specs/`):

| ID | Схема | Пример | Каталог |
|---|---|---|---|
| VF (функция) | `VF<d>.<d>` | `VF1.1`, `VF6.2` | `specs/vision.md` §2.2 |
| UC | `UC-<L1>.<L2>.<L3>` | `UC-remote.session.connect-to-node` | `specs/use-cases/` |
| FR | `REQ-FR-<domain>.<qualifier>.<action>` | `REQ-FR-remote.session.establish-rfb-session` | `specs/fun-req/` |
| NFR | `REQ-NFR-<area>.<qualifier>.<attribute>` | `REQ-NFR-security.compliance.no-inbound-ports` | `specs/nonfun-req/` |
| BR | `BR-<тип>.<semantic-tag>` | `BR-integrity.no-inbound-ports` | `specs/business-rules/` |
| ADR | `ADR-<LEVEL>.<AREA>.<semantic-tag>` | `ADR-IMPL.SECURITY.vnc-auth-choice` | `specs/adr/` |
| Доменное событие | PascalCase | `VncSessionEstablished`, `VncStateChanged` | `specs/domain/domain-events.md` |

## Usage Patterns

### Формат меток трассировки

Канонический формат комментария-метки — ID в квадратных скобках или в начале строки после символа комментария; текст после `:` поясняет, *какая часть* требования реализована здесь:

```go
// StartRepeater устанавливает исходящее TCP-соединение с VNC Repeater (Mode II)
// и удерживает его до появления клиента.
//
// Реализует REQ-FR-remote.session.connect-via-repeater:
// узел не открывает входящих портов (BR-integrity.no-inbound-ports, VF1.3).
func (s *Server) StartRepeater(...) { ... }
```

Правила:
1. **Одна метка — один ID.** Если реализуются несколько требований, каждое — отдельной строкой-ссылкой.
2. **Только канонический ID.** Не «FR connect-via-repeater», не путь к `.md`, а полный устойчивый ID.
3. **Метку можно проверять скриптом/линтером**: все `REQ-FR-*`, `REQ-NFR-*`, `BR-*`, `UC-*`, `VF*` в коде должны существовать в `specs/` (обратный grep). «Висячая» метка = расхождение реализации и требований.
4. **Не дублировать текст требования** — описывать связь кратко («реализует», «критерий 3», «ограничено правилом»).
5. В Go doc-комментариях метку размещать отдельным абзацем после описания контракта — так её не теряет `go doc`.

### Куда вешать метку

| Реализация | Метка | Пример |
|---|---|---|
| Метод/функция целиком реализует FR | doc-комментарий функции | `REQ-FR-remote.session.establish-rfb-session` |
| Ветка кодирует BR | inline-комментарий над `if`/`switch` | `BR-action.access-code-rotated-after-session` |
| Константа/формат подчинены NFR или протоколу | doc-комментарий константы | `REQ-NFR-security.compliance.rfb-tls` |
| Установка/проверка инварианта агрегата | inline-комментарий у вызова | инвариант + связанный `BR-*` |
| Код порождает доменное событие | inline-комментарий у публикации события | `VncSessionEstablished` |
| Ограничение/исключение для платформы | `//go:build`-файлы, inline | `REQ-NFR-infra.compliance.platform-support` |
| Тест проверяет критерий приёмки FR | имя теста `TestXxx_REQFR…`, комментарий | `TestEstablishRFBSession_VNCAuth` |

### Проверка соответствия критерию приёмки в тестах

Критерии приёмки FR нумерованы (см. файлы `specs/fun-req/`). Тест, покрывающий конкретный критерий, помечается так, чтобы критерий был находим:

```go
// Покрывает REQ-FR-remote.session.establish-rfb-session, критерий 2:
// тип Security согласуется по наличию кода доступа (VNC Auth / None).
func TestNegotiateSecurity_TypeDependsOnAccessCode(t *testing.T) { ... }
```

### Комментарии для неочевидного в коде VNC (реальные образцы)

```go
// internal/vnc/session.go — согласование версии RFB. Комментарий-намерение.
// negotiateVersion — согласование версии протокола RFB с клиентом.

// internal/app/app.go — причина выбора (почему, а не что).
// Доработка для UltraVNC Repeater
const repeaterHeaderSize = 250 // Байт

// internal/app/app.go — назначение колбэка доменным языком.
// CaptureHookProcess вызывается после каждого захвата кадра для постобработки.
// Используется для маскировки пикселей оверлея перед отправкой VNC-клиенту.

// internal/overlay/overlay.go — контракт + платформенное исключение.
// MaskFrame перезаписывает пиксели граничных полос захваченного кадра
// контентом из ближайшей внутренней строки/столбца, скрывая рамку от VNC-клиента.
// На Windows нет необходимости: SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE) исключает оверлей из захвата.

// internal/vnc/const.go — доменный/протокольный смысл константы.
// VNCPasswordKeyLenght длина ключа DES для VNC-аутентификации (RFB VNCAuth, всегда 8 байт)
```

Каждый из этих комментариев удалить нельзя без потери знания. Обратите внимание: комментарий `MaskFrame` — эталон — объясняет *что делает метод на доменном языке*, *какую проблему решает* и *где исключение*.

## Best Practices

1. **Пиши «почему» и «какое правило», а не «что делает код».** Если хочется прокомментировать механику — переименуй в выразительную функцию/переменную (Clean Code: «комментарий не компенсирует плохой код»).
2. **Используй Ubiquitous Language.** Термины — из `specs/glossary.md` (`VNC-сессия`, `код доступа`, `репитер`, `кассовый узел`, `фреймбуфер`, `оверлей`). Один доменный термин = одно значение; не вводи синонимы в комментариях.
3. **Называй инварианты и BR по имени.** Где код устанавливает/проверяет инвариант агрегата или следует бизнес-правилу, комментарий называет правило и (при наличии) вешает ID `BR-*` / `REQ-*`.
4. **Ставь метку трассировки на реализацию требования.** FR/NFR/BR/UC/VF реализованы → doc-комментарий публичного символа содержит канонический ID. Это делает цепочку `Vision → UC → FR → COMP → TEST` проверяемой из кода.
5. **Комментируй контракт, а не реализацию.** Doc-комментарий экспортируемого символа: первое предложение — имя символа + что он делает/возвращает/гарантирует (Go Doc Comments). Внутренние детали алгоритма — не в doc-комментарий.
6. **Объясняй неочевидные константы и магические числа** (протокольные размеры, смещения, ключи): смысл числа + источник (RFC/RFB/репитер/платформа). Пример: `const repeaterHeaderSize = 250 // Байт` + причина.
7. **Фиксируй платформенные различия у места ветвления.** Windows/Linux/другое — отдельные файлы (`*_windows.go`, `*_linux.go`), а исключения в общем коде поясняются ссылкой на API платформы (`WDA_EXCLUDEFROMCAPTURE` и т.п.).
8. **Помечай TODO/долг ссылкой на задачу или open question**, а не голым «TODO»: `TODO(RNDHWP-XXXX): ...` либо ссылкой на `specs/open-questions.md`. Голый TODO без владельца — шум.
9. **Отмечай подавление предупреждений линтера с причиной.** В коде уже принят стиль `// #nosec G115 -- len предварительно ограничен math.MaxUint32`: причина подавления обязательна.
10. **Метки делай проверяемыми.** Все ID в комментариях должны резолвиться в `specs/`. Добавь в CI/`golangci-lint` проверку «комментарий-метка ↔ существующее требование».
11. **Комментируй изменения в терминах требования.** При изменении поведения сначала ответь, какое FR/BR меняется; комментарий и код меняются вместе, иначе метка устаревает.
12. **Тесты — исполняемая спецификация** (DDD): имя теста и комментарий выражают бизнес-правило на Ubiquitous Language и ссылаются на критерий приёмки FR.

## Common Pitfalls

| Ошибка | Пример | Как избежать |
|---|---|---|
| **Зеркалирование кода** | `// Читаем выбор клиента` перед `st, err := rw.ReadByte()` | Писать намерение: «проверяем, какой тип Security выбрал клиент»; либо удалить |
| **Пересказ без знания** | `// Увеличиваем счётчик на 1` | Удалить; код самодокументируем |
| **Дублирование текста требования в коде** | комментарий повторяет абзац FR целиком | Оставить только канонический ID + короткую связь |
| **Изобретённый/«висячий» ID** | `// REQ-FR-...` которого нет в `specs/fun-req/` | Проверять метки скриптом; ID только из каталогов `specs/` |
| **Синонимы доменных терминов** | «затемнение экрана» вместо «скрытие рабочего стола» | Сверяться с `glossary.md` и `domain/` |
| **Комментарий об алгоритме в doc-комментарии** | описание сортировки внутри `// Sort ...` | Doc = контракт; детали реализации — внутри функции |
| **Закомментированный код** | `// if x { ... }` в проде | Удалять; историю хранит git |
| **Шумовые маркеры/журнал изменений** | `// 2026-01-01: исправлено ...` | Удалять; историю хранит git, трассировку — метки |
| **Метка устарела после изменения поведения** | функция всё ещё помечена FR, но уже не реализует его критерий | Обновлять метку при каждом изменении контракта |
| **Комментарий «что» вместо «почему» в ветке BR** | `// если режим auto` | `// auto: ротация кода доступа после завершения сессии (BR-action.access-code-rotated-after-session)` |

## Внедрение в проект VNC

1. **Пакетная документация.** Добавить package-комментарии в `internal/vnc`, `internal/app`, `internal/mdl`, `internal/overlay` (Go: «Package … implements …»). В package-комментарии `internal/vnc` указать связь с `REQ-FR-remote.session.establish-rfb-session` и контекстом `vnc-session` из `specs/domain/`.
2. **Doc-комментарии экспортируемых символов** — первое предложение с именем символа (стандарт Go), затем абзац доменного смысла, затем метки.
3. **Инварианты приватности** (`specs/domain/README.md` п. 6): у вызовов скрытия/восстановления рабочего стола (`setBlackWallpaper`, `restoreWallpaper`, overlay) — комментарий с именем инварианта и `BR-action.screen-concealed-during-session` / `REQ-FR-remote.screen.conceal-desktop`.
4. **Auth/security-код** (`internal/vnc/auth.go`, `negotiateSecurity`): пометить `REQ-FR-remote.session.authenticate-client`, `BR-integrity.vnc-password-eight-bytes`, а проверки None/VNC Auth — критериями приёмки.
5. **gRPC/ACL-слой** (`internal/mdl`, `proto/vnc_mdl.proto`): комментарии, объясняющие порт в платформу (`mdl`) как Anti-Corruption Layer — доменным языком из `specs/domain/README.md` п. 2.
6. **Проверка меток в CI** — маленький скрипт: собрать `REQ-(FR|NFR)-*`, `BR-*`, `UC-*` из `.go` и сверить с именами файлов `specs/*/REQ-*.md`, `BR-*.md`, `UC-*.md`.
