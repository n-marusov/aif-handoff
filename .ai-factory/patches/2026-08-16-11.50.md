# Unauthenticated git sync/publish routes

**Date:** 2026-08-16
**Files:** packages/api/src/routes/gitlab.ts, packages/api/src/routes/github.ts, docs/api.md
**Severity:** medium

## Problem

`POST /projects/:id/gitlab/sync`, `.../gitlab/tasks/:taskId/publish` (and the GitHub
equivalents) mutated task state and could be reached by any caller without
authentication. The provider/rollout middleware only gated on `GIT_PROVIDER` + feature
flag. `npm audit` also surfaced 4 high-severity dev-dependency advisories.

## Root Cause

The routes were built to be called by the agent, which already sends
`internalApiHeaders()` (Bearer / `X-Internal-Broadcast-Token` when
`INTERNAL_BROADCAST_TOKEN` is configured), but the server never verified the token on
these specific routes — unlike `POST /tasks/:id/broadcast`, which uses
`internalBroadcastAuth`. The auth gap was an oversight in the original GitHub/GitLab
Issue-to-MR work.

## Solution

Applied `internalBroadcastAuth` middleware to the sync and publish routes in both
`routes/gitlab.ts` and `routes/github.ts`. The middleware:
- enforces `INTERNAL_BROADCAST_TOKEN` (Bearer or header) when configured,
- bypasses in tests (`NODE_ENV=test`),
- rejects with 401 otherwise.

Added a regression test asserting 401 without the token and no upstream fetch; updated
`docs/api.md` wording from "may use" to "must provide". Deployments must set
`INTERNAL_BROADCAST_TOKEN` in `.env` (docker-compose already reads `env_file: .env`).
Also ran `npm audit fix` to clear the high-severity dev advisories.

## Prevention

- Any route that only the agent calls should mount `internalBroadcastAuth`; when adding a
  new internal API surface, mirror `POST /tasks/:id/broadcast`.
- When a code-review finding says "routes lack auth", verify the deployment's
  `INTERNAL_BROADCAST_TOKEN` is actually configured before shipping the enforcement —
  the middleware rejects unconfigured production callers.
- Run `npm audit` in CI (fail on high) so transitive dev advisories surface early.
