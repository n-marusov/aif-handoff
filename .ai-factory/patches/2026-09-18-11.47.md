# GitLab plan review: vacuous `approved: true` swallowed the approval edge; merge ignored at `review`

**Date:** 2026-09-18 11:47
**Files:** packages/api/src/services/gitlab.ts, packages/api/src/routes/gitlab.ts, packages/data/src/gitlab.ts, docs/gitlab-demo.md
**Severity:** high

## Problem

1. A task parked in `plan_review` never advanced to `implementing` after a
   human clicked **Approve** on the GitLab MR. No error was surfaced anywhere;
   the coordinator's GitLab sync simply never acted on the event.
2. A task in `review` stayed stuck when a human **merged** the implementation
   MR: the merge event was ignored entirely.

## Root Cause

Two compounding defects:

1. **Vacuous approval on GitLab EE.** `latestReviewState()` mapped
   `approvals.approved === true` to `reviewState: "approved"`. But per GitLab
   docs, on EE (which includes gitlab.com projects without configured approval
   rules, e.g. the free tier's default `any_approver` rule with
   `approvals_required: 0`) the `/merge_requests/:iid/approvals` endpoint
   returns `approved: true` even with an **empty** `approved_by` list — nobody
   has approved yet. So `publish-plan` itself persisted `reviewState:
   "approved"` at MR creation, and the sync edge trigger
   `approvals.reviewState === "approved" && existing?.reviewState !== "approved"`
   could never observe a pending → approved rising edge. The Approve click was
   structurally invisible.

2. **Burned edge markers (same incident class as the 2026-09-11 GitHub
   patch).** `updateGitLabMergeRequest()` persisted the review edge markers
   (`reviewState`, `lastReviewNoteId`) before the `markTaskPlanApproved` /
   `markTaskPlanChangesRequested` CAS transitions ran, and the route ignored
   their `TaskTransitionResult`. Any transient conflict permanently swallowed
   the review event — a known failure mode that had only been fixed on the
   GitHub side (cross-adapter sync rule violation).
3. **Merged branch gated on `done` only.** The sync merged-handling required
   `task.status === "done"`, so a task still in `review` (manual handoff or
   auto-review gate disabled) was left untouched when the human merged the MR
   — even though a merge is the strongest possible human acceptance signal.

## Solution

- `latestReviewState()` now requires a real approval: `approved === true`
  **and** non-empty `approved_by` — deterministic across CE/EE/Premium.
- Approval is edge-triggered from the MR **system note** "approved this merge
  request" (new `findLatestApprovalNote()` helper, same tier-agnostic channel
  already used for "requested changes"), with latest-note-id-wins conflict
  resolution between approval and changes-requested notes.
- The `lastReviewNoteId` marker is recorded only after the transition
  succeeds, via new targeted data helper
  `updateGitLabMergeRequestLastReviewNoteId()` (mirrors
  `updateGitHubPullRequestLastReviewId`). Return values of both
  `markTaskPlan*` functions are checked; failures log at ERROR and retry on
  the next sync.
- Merged MR now completes `review` as well: the sync chain runs
  `review → done → accepted` in one pass (re-reading the task between CAS
  transitions), then performs the existing worktree cleanup.
- Test-only fix: `gitlab.test.ts` now no-ops `callAgentSubmoduleSync` via
  `vi.mock` of the bridge, and `github.test.ts`'s existing bridge mock gained
  the same export. Since commit 89550e8 the sync routes call the submodule
  bridge: in GitLab tests it consumed the first entry of every stubbed fetch
  chain (misaligning all sync assertions); in GitHub tests the missing export
  made the fire-and-forget call throw a TypeError before the route's try
  block.

## Prevention

- When mirroring a fixed failure mode across provider routes (GitHub ↔
  GitLab), scan for every VCS route variant — the 2026-09-11 incident fix
  covered only `routes/github.ts`. Note `routes/github.ts` still has the
  merged-requires-`done` gap (#3 above); port if GitHub mode reports it.
- Never treat a license-tier-dependent boolean as an event; use the event
  itself (system note id) as the edge trigger.
- A human merge/approve on the remote is an acceptance signal; every terminal
  VCS transition should accept any still-open pre-terminal stage rather than
  a single hard-coded status.
- New fire-and-forget global-fetch calls inside routes break every
  `mockResolvedValueOnce` chain downstream; prefer module-level seams
  (`vi.mock` of the bridge) in tests instead of implicit fetch-count coupling.
