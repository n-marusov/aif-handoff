# GitLab plan-review fix left stale docs and an untested note-race branch

**Date:** 2026-09-18 12:59
**Files:** docs/api.md, docs/architecture.md, docs/configuration.md, packages/api/src/__tests__/gitlab.test.ts
**Severity:** low

## Problem

`/aif-verify` on the 2026-09-18 GitLab plan-review fix (see
`2026-09-18-11.47.md`) found the code green but two follow-up gaps:

1. Three documentation files still described the **pre-fix** behavior:
   "review state is approvals-only: `approved` when the approvals endpoint reports
   `approved=true`", "a merged MR advances a MR-ready `done` task to accepted", and
   "`last_review_note_id` persisted on every sync". After the fix, `approved` additionally
   requires a non-empty `approved_by` list, the plan-review gate edge-triggers from the
   "approved this merge request" system note (not the approvals boolean), merged MRs
   complete a task parked at `review` as well, and the marker is recorded only after a
   successful transition.
2. The new route-level conflict-resolution branch (when an approval note and a
   requested-changes note are both unprocessed, the higher note id wins) had no
   regression test.

## Root Cause

- The fix patch updated only the file listed in its own `**Files:**` header
  (`docs/gitlab-demo.md`). The same behavioral sentences exist in `docs/api.md`,
  `docs/architecture.md`, and `docs/configuration.md` — the "enumerate ALL occurrences"
  lesson from the fix's own Prevention section applied to docs, not just adapters.
- The race branch was written as a defensive tie-breaker, so no scenario forced a test
  for it during the original TDD pass.

## Solution

- Rewrote the GitLab sync/plan-review paragraphs in `docs/api.md`, the GitLab workflow
  section (and its `Verified` → `Accepted` terminal-state wording, which pre-dated the
  state rename in 4e99cfd) in `docs/architecture.md`, and the two approvals-only
  sentences in `docs/configuration.md` to match the implemented note-driven,
  marker-after-transition behavior.
- Added two route tests to `packages/api/src/__tests__/gitlab.test.ts` driving the
  competing-notes sync with both orders (approval newer → `plan_review → implementing`
  with `planReviewState=approved` and marker at the approval id; requested-changes newer
  → `planning` with `planReviewState=changes_requested` and marker at the changes id).
  Both stub the vacuous EE approvals payload (`approved=true`, empty `approved_by`) so
  the tests also pin that the boolean alone cannot drive the transition.
- No production-code change: the implementation, typecheck (tsc api), lint, and the
  full `@aif/api` + `@aif/data` suites were already green in the verify pass.

## Prevention

- When a fix changes behavior described in docs, grep every doc for the old phrasing
  (`approvals-only`, `approved=true`, state names) — behavior descriptions live in
  api/architecture/configuration/demo docs simultaneously.
- Any newly added tie-breaker/conflict branch gets a table-driven test in the same
  commit, even if the original incident did not exercise it.
- Verification reports listing "docs updated: file X" should be read as "only file X was
  updated" — cross-check sibling docs for the same sentences.
- Stale state-name drift (`Verified` after the `verified → accepted` rename) still exists
  in `docs/architecture.md` around the GitHub workflow (lines ~114/165/182); a future
  docs pass should normalize it everywhere.
