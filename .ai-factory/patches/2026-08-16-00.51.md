# GitLab connect times out in UI while the clone completes server-side

**Date:** 2026-08-16 00:51
**Files:** packages/web/src/lib/api.ts, packages/web/src/components/project/ProjectSelector.tsx, .docker/angie.conf, .docker/angie.production.conf, packages/web/src/__tests__/api.test.ts
**Severity:** medium

## Problem

Clicking the GitLab "Connect" button cloned the repository successfully on the
backend, but the UI showed a timeout instead of a success toast. The user saw
the repository appear locally while the browser reported a failure.

## Root Cause

The GitLab connect endpoint (`PUT /:id/gitlab`) runs a synchronous best-effort
`git-prepare` via `callAgentGitPrepare`, which performs a real
`git fetch/checkout/commit` and is allowed up to 120s by the server-side bridge
(`gitlabPrepareBridge.ts`). The frontend, however, called
`connectProjectGitLab` through the generic `request()` helper without a custom
timeout, so it used the default `REQUEST_TIMEOUT_MS = 15_000`.

Because `performRequest` wraps every call in `setTimeout(() => controller.abort(), timeoutMs)`,
the browser aborted the fetch at 15s while the agent kept cloning in the
background. The clone finished, but the UI had already thrown
`Request timed out after 15000ms`.

A second, latent issue: in Docker the `/api/` reverse proxy (Angie) has no
`proxy_read_timeout`, so it falls back to the nginx/angie default of 60s. Even
after the client timeout was raised, the production proxy would still cut the
connect response before the up-to-120s prepare finished.

## Solution

- Added `GITLAB_CONNECT_TIMEOUT_MS = 180_000` and
  `GITLAB_SYNC_TIMEOUT_MS = 300_000` to `packages/web/src/lib/api.ts` and
  passed them as the `timeoutMs` argument in `connectProjectGitLab` and
  `syncProjectGitLab` respectively. Connect covers the 120s prepare plus the
  GitLab API check; sync covers the strict prepare plus paginated issue/MR API
  calls.
- Added `[FIX]` error logging in the GitLab connect/sync `onError` handlers in
  `ProjectSelector.tsx` so any future timeout is observable in the console.
- Added `proxy_read_timeout 300s;` to the `/api/` location in both Angie configs
  so the production reverse proxy allows long-running API calls (GitLab
  prepare, chat, roadmap import).
- Added two fake-timer tests proving GitLab connect and sync do not abort at the
  old 15s default and resolve normally.

## Prevention

- Any API call that can outlive the default 15s `REQUEST_TIMEOUT_MS` must pass an
  explicit timeout budget to `request()`. Look at the backend handler's worst-case
  duration (including synchronous agent/git work) before wiring a new mutation.
- When a backend route intentionally blocks on a long sub-operation, verify the
  full path end-to-end: browser timeout, dev proxy, and production reverse proxy
  (`proxy_read_timeout`). A single-layer timeout fix is usually not enough.
- Add a fake-timer test asserting the `AbortSignal` is not aborted at the default
  budget for long-running mutations.
