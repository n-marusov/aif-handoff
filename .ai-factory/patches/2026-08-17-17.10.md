# GitLab MR publish aborted by 30s client timeout before API could respond

**Date:** 2026-08-17 17:10
**Files:** packages/shared/src/env.ts, packages/agent/src/gitlabWorkflow.ts, packages/agent/src/githubWorkflow.ts, packages/agent/src/__tests__/gitlabWorkflow.test.ts, packages/agent/src/__tests__/hooks.test.ts, docs/configuration.md
**Severity:** high

## Problem

A task moved to `blocked_external` from `implementing` with reason
`GitLab merge request publication is unavailable. Check the API service and retry.`
(`retryAfter=manual`, `source=none`).

The API service was healthy. Logs showed the real cause:

```
api:   GET /merge_requests/1/approvals  → TimeoutError (DOMException, code 23) after ~30s
api:   POST .../gitlab/tasks/.../publish  → 502 gitlab_upstream, duration 31738ms
agent: "GitLab merge request API unavailable", error:{}  (empty!)
```

The agent aborted its own 30s `AbortSignal.timeout` at ~30.0s, *before* the API
returned 502 at ~31.7s. So the agent saw a fetch rejection, not an HTTP error,
and reported "unavailable" while the API was still working.

## Root Cause

1. The GitLab upstream call `getMergeRequestApprovals` (`GET /merge_requests/{iid}/approvals`)
   hung and hit its own 30s timeout. The API publish handler runs several upstream
   GitLab/GitHub calls sequentially (find/get → create/update → checks+approvals), so it
   legitimately needs more than 30s total.

2. The agent's publish `fetch` used a hardcoded `AbortSignal.timeout(30_000)`. That 30s
   ceiling was *shorter* than the API's legitimate processing time, so the client aborted
   first — converting a slow-but-alive upstream into a false "unavailable" block.

3. The agent logged the fetch error with pino field `error` instead of `err`. Pino only
   runs its error serializer for the `err` key, so a `DOMException` (which has no
   enumerable own properties) serialized to `{}`. The actual cause was invisible from the
   agent log alone.

## Solution

- Added `AGENT_GIT_PUBLISH_TIMEOUT_MS` env var (default `120000`, i.e. 2 min) so the
  agent's publish fetch can be tuned without a code change. The default is longer than the
  API's upstream calls so the client waits for a real HTTP response (success or 4xx/5xx)
  instead of aborting mid-flight.
- Replaced the hardcoded `AbortSignal.timeout(30_000)` in both `publishGitLabTask` and
  `publishGitHubTask` with `AbortSignal.timeout(getEnv().AGENT_GIT_PUBLISH_TIMEOUT_MS)`.
  The background sync paths intentionally keep their 30s timeout (they are best-effort and
  retried on the next poll).
- Changed the error log fields from `error` to `err` in the six catch blocks across
  `gitlabWorkflow.ts` and `githubWorkflow.ts`, so pino serializes the error object (name,
  message, stack) instead of `{}`.
- Documented the new env var in `docs/configuration.md`.
- Added a test asserting the publish fetch uses the configured timeout.

## Prevention

- When a client `fetch` calls an internal service that itself fans out to slow upstreams,
  the client timeout must exceed the service's worst-case processing time — otherwise the
  client aborts and misreports a transient upstream delay as an outage.
- Always log error objects with pino's `err` key (not a custom field like `error`), or the
  error is silently dropped to `{}`.
- Two follow-ups identified but out of scope for this fix:
  - `GitLabClient.isRetryableNetworkError` (packages/api/src/services/gitlab.ts) guards with
    `!(error instanceof TypeError)` before checking `error.name === "TimeoutError"`, so the
    `AbortSignal.timeout` DOMException is never retried — dead code, confirmed by logs (1
    TimeoutError, 0 retries).
  - The publish route does not observe `c.req.raw.signal`, so aborted requests keep running
    upstream and can create an orphaned MR.
