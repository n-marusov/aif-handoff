# Web UI unreachable in localhost demo: plain-HTTP-on-443 400 + broken HTTPS redirect

**Date:** 2026-08-14 23:45
**Files:** `.docker/angie.production.conf`, `docker-compose.production.yml`, `docs/gitlab-demo.md`
**Severity:** medium

## Problem

Local demo with the default `DOMAIN=localhost`:

1. `http://localhost:443/` → `400 Bad Request: The plain HTTP request was sent to HTTPS port` (nginx/angie standard response for plain HTTP on an SSL listener).
2. `http://localhost/` (port 80) → `301` → `https://localhost/` → **TLS handshake fails** (exit 35) because Let's Encrypt cannot issue a certificate for `localhost` (no public DNS). Web logs: `cannot load certificate "/etc/angie/": PEM_read_bio_X509_AUX() failed`.

Net effect: the Web UI was unreachable from a browser in the localhost demo.

## Root Cause

- The production Angie config unconditionally redirected `:80 → https://$host$request_uri`, assuming a real domain with a valid ACME cert.
- The ACME client (`challenge=http`, Let's Encrypt) can never issue for `localhost`/`127.0.0.1`, so the `listen 443 ssl` block had an empty/missing cert path and every TLS handshake failed.
- Hitting `http://localhost:443/` directly is plain HTTP to an SSL port — nginx/angie returns 400 before any server block can intercept it.

## Solution

Split the port-80 listener by `server_name`:

- `localhost 127.0.0.1 [::1]` → serve the SPA directly on `:80` (`try_files $uri $uri/ /index.html`). `http://localhost/` now returns `200` with the Web UI.
- `${DOMAIN}` → keep the ACME challenge location and `301 → https://` for real deployments.

Updated the web container healthcheck to assert `HTTP/1.1 200` (it previously asserted the 301 that localhost no longer emits). Verified: `curl http://localhost/` → 200 SPA; container `(healthy)`; the 400 on `http://localhost:443/` remains (expected — it is the HTTPS port; plain HTTP there is a client error, and the correct entry point is now `http://localhost/`).

## Prevention

- Localhost demos must not be forced through HTTPS: Let's Encrypt cannot certify `localhost`, so a `:80 → https` redirect with `DOMAIN=localhost` is a dead end.
- When changing web server redirect behavior, update the compose healthcheck in the same change (it asserted the old 301 signal).
- Document the correct entry point: `http://localhost/` for local demos, `https://<DOMAIN>/` for real deployments.
