# Runtime capability fallback skipping unconfigured runtime candidates

**Date:** 2026-09-13 08:55
**Files:** packages/agent/src/subagentQuery.ts
**Severity:** high

## Problem

When a task's selected runtime (e.g., openrouter/api) lacks `supportsWorkspaceTools`, the
`fallbackToWorkspaceToolRuntime()` function falls back to the first registered runtime that
advertises workspace capabilities. It iterates `["claude", "codex", "opencode"]` in order
and picks the first one with `supportsWorkspaceTools === true` — regardless of whether that
runtime is actually configured with credentials.

In the reported case, OpenRouter (API transport, no workspace tools) was the task runtime.
The fallback chose Claude SDK (which advertises `supportsWorkspaceTools: true`) even though
`ANTHROPIC_API_KEY` was not set and the user was not logged in to Claude Code. The Claude SDK
then failed with `CLAUDE_AUTH_ERROR: Not logged in`. This created an infinite loop:
`blocked_external` → backoff → retry → same `CLAUDE_AUTH_ERROR` → repeat, wasting hours.

## Root Cause

The `fallbackToWorkspaceToolRuntime()` function resolved ad-hoc runtime profiles with
`profile: null` (no DB profile lookup) and checked only `supportsWorkspaceTools` on the
adapter's declared capabilities. It never verified whether the candidate runtime had the
_minimum required credentials_ (API key, CLI path) before committing to the fallback.

The resolution step (`resolveRuntimeProfile`) succeeded with `apiKey: null` because it
merely maps env vars — it doesn't fail when the env var is unset. This is correct behavior
for normal profile resolution (where the adapter may use fallback auth like OAuth), but
for an ad-hoc fallback profile with no DB backing, `apiKey: null` reliably means "not
configured."

## Solution

Added a credential check in `fallbackToWorkspaceToolRuntime()` after the capability check.
For each candidate runtime:

1. Resolve its ad-hoc profile (existing behavior)
2. Check `supportsWorkspaceTools` (existing behavior)
3. **NEW:** If the candidate has no DB profile (`profileId === null`) and uses a transport
   that requires an API key (SDK or API transport), verify that `apiKey` is non-null.
   If missing, skip the candidate with a warning log.

If ALL candidates are skipped due to missing credentials, the function now logs a detailed
warning (with guidance to the user) and returns the original runtime. The caller then hits
`assertRuntimeCapabilities()` which throws `RuntimeCapabilityError` with a clear message
like `Runtime "openrouter" does not support required capabilities: supportsWorkspaceTools`,
breaking the infinite retry loop.

## Prevention

- Always verify that ad-hoc fallback candidates have the minimum required credentials before
  falling back — a runtime with `apiKey: null` and no DB profile will fail at execution.
- The capability fallback should be credential-aware: `supportsWorkspaceTools` only indicates
  _potential_ capability, not actual readiness.
- Consider adding a lightweight `validateConnection()` check to the fallback loop for more
  accurate readiness detection in the future.
