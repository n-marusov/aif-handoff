# Stale completed plan file reused by new issue task

**Date:** 2026-09-10 14:30
**Files:** packages/agent/src/subagents/planner.ts
**Severity:** medium

## Problem

When a new task is created for a GitHub/GitLab issue whose plan file (`.ai-factory/plans/github-issue-<N>.md`) already exists **committed in the repo** with all `**Task N:**` checkboxes completed, the planner finds the existing file and treats it as the current plan. The implementer then sees all tasks done and skips execution → `blocked_external` via auto-queue commit gate. The user sees: "Implementer no-op: all plan tasks already completed."

Manifestation: `scanned:0, removed:0, repaired:0, adoptedLegacy:0` in reconciliation; the plan file on disk shows a completely unrelated plan (e.g. "Обогащение кода..." instead of the issue's description).

## Root Cause

The plan path for VCS-linked tasks is deterministic: `github-issue-<N>.md`. When this file is committed to the repository (user's explicit choice — plans are version-controlled), every new worktree inherits it. The planner dispatches a subagent with `@.ai-factory/plans/github-issue-<N>.md`, the subagent reads the existing file, sees all tasks `[x]`, and either writes it back as-is or writes nothing. `planReviewFeedback` is null for a first-time planning, so the planner doesn't know this is a stale artifact.

Key insight: an all-`[x]` plan at the target path for a brand-new task is **always** stale in VCS-linked flows — nothing should be completed before the first planner run.

## Solution

Added a pre-flight check in `runPlanner()`: after provisioning the branch/worktree but before dispatching the subagent, read the plan file from disk. If it exists and `computePlanLayers()` reports every task as `completed`, delete the file. The subagent then starts with an empty target and generates a fresh plan from the issue description.

Guard conditions:
- Only fires when `planReviewFeedback` is falsy (first-time planning, not replanning)
- Only for non-`isFix` tasks
- Non-fatal on unparseable plan text or filesystem errors

## Prevention

- This check covers all VCS-linked task paths (GitHub/GitLab) with committed plan files.
- For non-VCS tasks, the default plan path (`PLAN.md`) is less likely to collide across runs, but the same check protects them too.
- The `computePlanLayers` call already parses the plan; no separate parser needed.
