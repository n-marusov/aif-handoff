# Git submodules not initialized during repository prepare

**Date:** 2026-09-16 23:12
**Files:** packages/agent/src/repositoryPrepare.ts, packages/agent/src/__tests__/gitlabPrepare.test.ts, packages/agent/src/submoduleSync.ts, packages/agent/src/internalApi.ts, packages/api/src/services/gitPrepareBridge.ts, packages/api/src/routes/gitlab.ts, packages/api/src/routes/github.ts
**Severity:** medium

## Problem

When connecting a GitLab or GitHub repository that uses git submodules
(has `.gitmodules` file), the Sync now flow executes `git fetch` and
`git checkout` but does NOT initialize submodules. The working tree
remains incomplete — submodule directories are empty — which causes
failures when AI subagents try to read code or run git operations
that depend on submodule content.

Additionally, the credential helper was only set at the repository level
(`git config credential.helper ...` without `--global`). When `git submodule
update --init --recursive` runs, it spawns `git clone` for each submodule,
which creates a new git repository. The new repo does NOT inherit the
parent's repo-level credential helper, so git falls back to an interactive
password prompt, which fails in a headless container with
"could not read Username: No such device or address".

Finally, the submodule init only ran during the initial git-prepare step.
For projects that were already connected before the submodule feature was
deployed, `gitPreparedAt` was already set, prepare was never called again,
and submodules were never initialized.

## Root Cause

Triple root cause:

1. **Missing submodule init step:** The `prepareRepository` function
   performs a sequence equivalent to `git clone` (init → remote → fetch
   → checkout) but omits the standard `git submodule update --init
   --recursive` step that real `git clone --recurse-submodules` would
   execute. Without this step, projects that use submodules for shared
   libraries, pinned dependencies, or monorepo splitting get an empty
   working tree.

2. **Repo-level credential helper insufficient for submodule clones:**
   The credential helper was set as `git config credential.helper ...`
   (repo-level). When `git submodule update --init --recursive` runs,
   it clones each submodule via `git clone`, which creates a separate
   git repository. The clone process reads the credential helper from
   the global config, not from the parent repo's local config, so the
   token is not available and authentication fails.

3. **Submodule init not repeated on subsequent syncs:** The submodule
   init step was part of `prepareRepository`, which only executes during
   the initial git-prepare when `connection.gitPreparedAt` is null. For
   already-connected projects, prepare is never called again, so even
   with the new submodule step, submodules would remain uninitialized.

## Solution

1. **Added step 7 in `prepareRepository`** that checks for `.gitmodules`
   after checkout and runs `git submodule update --init --recursive` when
   the file exists. Idempotent — absence of `.gitmodules` is not an error.
   New error kind `submodule_failed` added to `RepositoryPrepareErrorKind`.

2. **Changed credential helper to global level:** In addition to the
   repo-level credential helper, also set it globally via
   `git config --global credential.helper ...` so that `git clone`
   operations spawned by `git submodule update --init --recursive`
   inherit the credentials.

3. **Added best-effort submodule sync on every sync:** Created a new
   `submoduleSync.ts` with `syncProjectSubmodules()`, a new endpoint
   `POST /submodules/sync` on the agent internal API, a bridge function
   `callAgentSubmoduleSync()`, and calls from both `gitlab.ts` and
   `github.ts` sync routes (fire-and-forget, non-blocking). This ensures
   that even already-connected projects get their submodules populated.

## Prevention

- Any git-prepare flow (GitHub or GitLab) must include submodule init
  to match the semantics of `git clone --recurse-submodules`.
- When adding new provider prepare flows, reuse the same check pattern:
  check for `.gitmodules` → `git submodule update --init --recursive`.
- Test coverage should include a project with `.gitmodules` to verify
  submodule init fires and a project without `.gitmodules` to verify
  the step is skipped.
- Git 2.38.1+ blocks the file:// protocol for security (`fatal: transport
  'file' not allowed`). Tests using local paths for submodules must
  enable `protocol.file.allow = always` globally. Production submodules
  typically use HTTPS URLs so this is not a concern at runtime.
- Credential helpers for submodule operations MUST be set globally
  (`--global`), not just at the repo level, because submodule clones
  create new git repos that don't inherit repo-level config.
- Submodule init must be callable independently from the prepare flow
  so already-connected projects can populate submodules on subsequent
  syncs.
