# Done tasks never transition to Accepted on GitHub /approve review comment

**Date:** 2026-09-15 10:30
**Files:** packages/api/src/routes/github.ts, packages/api/src/__tests__/github.test.ts
**Severity:** medium

## Problem

A task that reached `done` stayed `done` after a reviewer added an `/approve`
review comment (or an official APPROVED review) on the GitHub PR. Per the
requirement, a confirmed task must transition from `done` to `accepted`.

The agent log showed the task moving `review → done`, the PR being
synchronized, and then nothing further — the task never advanced to `accepted`.

## Root Cause

In `packages/api/src/routes/github.ts`, the GitHub sync handler computed
`effectiveReviewState` and `effectiveReviewId` (which treat a COMMENTED review
containing `/approve` as an approval), but that logic was only consumed by two
paths:

1. `prState === "merged"` && `status === "done"` → `accepted` (requires an actual
   PR merge, not just a review)
2. `status === "plan_review"` → plan-review gate (approve → implementing)

There was **no branch** mapping `status === "done"` + `effectiveReviewState ===
"approved"` to `accepted`. So an `/approve` comment (or official approval) on an
open PR left the task stuck in `done`.

## Solution

Added a new branch in the sync if/else chain, between the "PR closed → paused"
case and the "changes requested → implementing" case:

- Conditions: task is `done`, `effectiveReviewState === "approved"`, the review
  is new (`effectiveReviewId !== existing.lastReviewId`), and the PR is not
  merged/closed.
- Action: transition the task to `accepted` via `updateTaskStatus`, then record
  `lastReviewId` so the same review is not re-processed on a later sync cycle.
- Idempotency mirrors the merge and plan-review paths: the review ID is only
  persisted after a successful transition.

## Prevention

- When extending the GitHub sync review handling, audit **all** consumer paths
  of `effectiveReviewState`/`effectiveReviewId` — the `/approve` fallback is
  intentionally shared between the plan-review gate and the Done→Accepted gate,
  and adding a state without the corresponding transition branch silently
  breaks the requirement.
- Regression coverage: tests for done→accepted on official APPROVED, done→
  accepted on COMMENTED `/approve`, and no double-processing when `lastReviewId`
  already matches.
