# Stale coordinator claim blocks task when GitLab/GitHub sync touches updatedAt

**Date:** 2026-08-16 05:30
**Files:** packages/data/src/index.ts, packages/data/src/gitlab.ts, packages/data/src/github.ts, packages/data/src/__tests__/index.test.ts, packages/data/src/__tests__/gitlab.test.ts, packages/data/src/__tests__/github.test.ts
**Severity:** high

## Problem

A task stuck in `review` status never moved to `Done`. The coordinator polled every 30s with "No actionable project lanes", yet the task was locked by a coordinator that had crashed ~1h earlier (`lockedBy` set, `lockedUntil` 65 min in the future, `lastHeartbeatAt` stale).

`releaseStaleTaskClaims` (the dead-process reaper) should have released the orphaned claim after 5 minutes via the stale-heartbeat branch — but it did not. The task stayed blocked until the lock TTL expired (~65 minutes), after which the review stage re-ran.

## Root Cause

`releaseStaleTaskClaims` gated the stale-heartbeat branch on `lte(tasks.updatedAt, heartbeatDeadline)`:

```
and(
  inArray(tasks.status, ["planning", "improve", "implementing", "review", "verify"]),
  lte(tasks.updatedAt, heartbeatDeadline),   // ← the gate
  or(lastHeartbeatAt IS NULL, lte(lastHeartbeatAt, heartbeatDeadline)),
)
```

The `updatedAt` gate was meant to "avoid race with fresh claims" — but `updatedAt` is a general-purpose "last write" timestamp, not a liveness signal. `importGitLabIssueTask` (and its GitHub twin `importGitHubIssueTask`) **unconditionally** wrote `title/description/tags/paused/updatedAt` to the linked task on every sync (once per ~60-90s). That kept `updatedAt` perpetually fresh, so the reaper concluded the task was "recently active" and never released the dead process's lock.

The `updatedAt` gate was also unnecessary for the coordinator claim path: a claim is immediately followed (in the same synchronous tick) by `updateTaskStatus` → `transitionTaskStatus`, which writes `lastHeartbeatAt`. So a freshly-claimed coordinator task always has a fresh heartbeat by the time the reaper could observe it.

## Solution

1. **`releaseStaleTaskClaims`** now uses `lastHeartbeatAt` as the liveness signal and drops the `updatedAt` gate. QA locks (`lockedBy LIKE 'qa:%'`) are excluded from the early-release branch because QA runs never write a heartbeat — they must live until their lock TTL expires.
2. **`importGitLabIssueTask` / `importGitHubIssueTask`** now only write the linked task row when the synced content actually changed (title/description/tags/paused differ). Identical re-syncs no longer touch the task, restoring the invariant that `updatedAt` reflects genuine task activity. A `[FIX]` debug log records the skip.

## Prevention

- The dead-process reaper must key on `lastHeartbeatAt` (the agent-liveness signal), never on `updatedAt` (a general-purpose write timestamp that unrelated subsystems legitimately touch).
- Sync/import services must be idempotent: do not rewrite a row (or bump `updatedAt`) when nothing changed. Changed-content comparison is cheap and prevents timestamp pollution.
- When adding a new background service that writes to `tasks`, check whether it is falsely extending the liveness signal used by `releaseStaleTaskClaims`.
