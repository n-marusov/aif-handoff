# Explicit issue plan path loaded stale target PLAN fallback

**Date:** 2026-09-10 21:55
**Files:** packages/agent/src/subagents/planner.ts, packages/agent/src/__tests__/planner.test.ts
**Severity:** medium

## Problem

A GitHub issue task with an explicit task-specific plan path such as
`.ai-factory/plans/github-issue-3.md` could persist an unrelated old plan
from the target repository's `.ai-factory/PLAN.md`. The implementer then
saw all checklist items as already completed and skipped the task.

## Root Cause

`readPlanFromDisk()` appended generic fallback paths for every non-fix
planning run. That was safe only when the requested plan path was the
project default, but it was also applied to deterministic issue plan paths.
In task worktrees, `.ai-factory/PLAN.md` belongs to the target repository,
not to Handoff, so a committed stale plan there could outrank the fresh
inline planner result whenever the canonical issue plan file was not written.

## Solution

Added explicit task-plan detection in `readPlanFromDisk()`. For non-fix
planning runs with a custom plan path different from the configured default
plan path, the planner now reads only the canonical task path and any path
explicitly reported by the runtime result. It skips `.ai-factory/PLAN.md` and
`PLAN.md` generic fallbacks and logs the decision with a `[FIX]` prefix.

Added a regression test that creates a target-project `.ai-factory/PLAN.md`
with stale content, runs planning for `.ai-factory/plans/github-issue-3.md`,
and verifies the persisted task plan comes from the fresh inline result.

## Prevention

- Treat generic plan fallback files as compatibility paths only for default
  plan-path workflows.
- For VCS issue tasks, prefer deterministic task-specific plan files or the
  runtime's inline output over repository-level generic plan artifacts.
- Keep regression coverage for target repositories that already contain
  `.ai-factory/PLAN.md`.
