# GitLab e2e stand never created the root user (weak GITLAB_ROOT_PASSWORD)

**Date:** 2026-09-21 03:18
**Files:** scripts/e2e-docker.mjs, docker-compose.e2e.yml, .env.e2e.example, .env.e2e, packages/web/e2e/README.md, docs/qa/e2e-api-testing.md, docs/qa/e2e-gui-testing.md
**Severity:** high

## Problem

`make e2e` reported success while the GitLab test stand was unusable: the `root`
account did not exist, so PAT provisioning failed with `root user not found` and
the test-project API returned `401`. The orchestration script only logged
`WARNING`, so the failure was silent — the e2e suite "passed" against a stand
whose GitLab half was broken.

## Root Cause

Two independent defects.

1. `GITLAB_ROOT_PASSWORD=aif-e2e-root-password` did not pass GitLab's
   password-strength validation. The seed `db/fixtures/production/003_admin.rb`
   aborts with `Password must not contain commonly used combinations of words
   and letters` — the value contains the username `root`. Because the seed exits
   non-zero, the omnibus `rails_migration[gitlab-rails]` resource fails and the DB
   is left half-seeded (`002_default_organization.rb` ran, `003_admin.rb` did
   not). On later container starts `gitlab-ctl reconfigure` is skipped entirely
   because `/var/opt/gitlab/bootstrapped` exists, so root is never created.
   Confirmed in `/var/log/gitlab/reconfigure/<ts>.log`.

2. The GitLab readiness probe polled `/-/health` from the host. That route is
   served only to `monitoring_whitelist` (`127.0.0.0/8`, `::1/128`), so from the
   host (Docker gateway IP) it always returns `404`. `waitForHttp` accepted any
   status `< 500`, so the probe returned immediately even while GitLab was still
   booting — it never actually gated on readiness.

## Solution

- Changed `GITLAB_ROOT_PASSWORD` (and the compose/script fallbacks) to
  `Xq7Zt2Lm9Vb4Kp`: passes the strength check, contains no dictionary word and no
  username substring.
- Added an idempotent `ensureGitLabRootUser` step to `scripts/e2e-docker.mjs`.
  If `User.find_by_username('root')` is nil it creates the account with the same
  `Users::CreateService` used by the seed (password from `GITLAB_ROOT_PASSWORD`,
  `admin: true`, default organization, `skip_confirmation: true`). This makes
  provisioning self-healing for existing half-seeded volumes.
- Switched the GitLab readiness probe to `GET /users/sign_in` requiring a real
  `2xx` (new `requireOk` parameter on `waitForHttp`), so the wait is meaningful
  and host-reachable.
- Added a `rubyString` helper and used it for the injected password/token, so a
  value containing quotes cannot break the generated Ruby.
- Documented the constraint in `.env.e2e.example`, the compose header, and the
  e2e docs.

## Prevention

- Any deterministic credential injected into GitLab's own seeding must satisfy
  its password policy: no dictionary words and no username/email/name
  substrings. For `root`, avoid the literal `root`.
- Do not assume omnibus seeding is retried: once `/var/opt/gitlab/bootstrapped`
  exists, later boots skip reconfigure. Provisioning scripts should reconcile
  required state idempotently instead of relying on the first-boot seed.
- Readiness probes must require the status that actually proves readiness.
  Accepting `4xx` (`status < 500`) makes a probe vacuous when the endpoint
  legitimately returns `404` from outside (e.g. GitLab `monitoring_whitelist`).
- This project bans ticket-style `[FIX]` log markers in production source
  (`scripts/check-log-markers.mjs`); fixes use the component's neutral prefix
  (`[e2e-docker]`) instead.
- Validation: after `make docker-e2e-down && make e2e-docker`, assert that
  `users` contains `root` (admin) and that `GET
  /api/v4/projects/root%2Fe2e-target` with the PAT returns `200`.
