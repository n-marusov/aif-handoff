# Stabilize @aif/data failure triage and validation context

**Date:** 2026-09-22 01:23
**Files:** packages/data/src/gitlab.ts, packages/data/src/__tests__/gitlab.test.ts
**Severity:** medium

## Problem

`npm run ai:validate` was reported as failing at `@aif/data#test` and an additional
`@aif/data` test run previously stalled for a long time, making it unclear whether
there was a regression in the GitLab re-import ownership sync change.

## Root Cause

There were two independent issues:

1. The suspected `@aif/data` regression was not reproducible as a deterministic
   assertion failure. A/B verification (`git stash` clean tree vs working tree)
   showed the same intermittent long-running behavior in parallel test mode,
   indicating an environment/test-runner flake pattern rather than a direct logic
   break in the ownership-sync patch.
2. The concrete `ai:validate` failure in this session occurred later at `ai:perf`
   due to `EADDRINUSE` on API port `3009`, not due to `@aif/data` assertions.

## Solution

- Re-ran `@aif/data` tests in controlled modes and captured full logs to disk
  (`.tmp/data-test-full.log`, `.tmp/data-test-recheck.log`) to avoid truncated output.
- Executed A/B check using stash isolation to classify whether changes in
  `gitlab.ts` / `gitlab.test.ts` caused failures.
- Confirmed package stability with successful full `@aif/data` run and coverage.
- Isolated `ai:validate` blocker to a runtime environment port collision in `ai:perf`.

## Prevention

- When triaging flaky package failures, first capture full logs to files and avoid
  relying on truncated terminal tails.
- Use stash-based clean-tree A/B checks before reverting functional fixes.
- Before running full `ai:validate`, preflight-check critical dev/perf ports
  (`3009`, `3010`, `5180`) to avoid false negatives from `EADDRINUSE`.
