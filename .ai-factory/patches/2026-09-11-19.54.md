# Plan review stuck: approval detection can silently fail without retry

**Date:** 2026-09-11 19:54
**Files:** packages/api/src/routes/github.ts, packages/data/src/github.ts
**Severity:** high

## Problem

A task published to `plan_review` status stays there permanently even after
a human approves the plan PR (via `/approve` comment or formal approval).
The system logs "GitHub plan review approved" but the task does not
transition to `implementing`.

## Root Cause

The sync handler in `packages/api/src/routes/github.ts` had two bugs:

1. **lastReviewId was updated before the plan review check.** `updateGitHubPullRequest`
   on line 245 set `lastReviewId` (and `reviewState`) BEFORE the plan review
   approval check at lines 305-357. When `markTaskPlanApproved` experienced a
   transient CAS conflict (e.g. status changed between the read and the
   conditional update), the function returned `{ok: false}` but the caller
   ignored the return value — the log entry claimed approval succeeded while
   the task stayed in `plan_review`. On the next sync cycle, the guard
   `effectiveReviewId !== (existing?.lastReviewId ?? null)` became `false`
   because `lastReviewId` had already been set to the review's ID, so the
   approval was never re-detected.

2. **markTaskPlanApproved / markTaskPlanChangesRequested return values were
   unchecked.** Both functions return `TaskTransitionResult` which can be
   `{ok: false, code: "status_conflict"}` when the CAS update fails. The
   caller logged "success" regardless of the actual outcome, masking the
   failure and preventing any recovery.

## Solution

1. **Removed `lastReviewId` from the initial `updateGitHubPullRequest` call**
   in the sync handler (line 245). The PR metadata, review state, and checks
   are still updated, but the review-tracking ID is deliberately deferred.

2. **Added `updateGitHubPullRequestLastReviewId` to the data layer** — a
   single-field update function (`packages/data/src/github.ts`) that only
   touches `lastReviewId`, `lastSyncedAt`, and `updatedAt`.

3. **Checked the return value of `markTaskPlanApproved` and
   `markTaskPlanChangesRequested`.** The review ID is now recorded via
   `updateGitHubPullRequestLastReviewId` only AFTER a successful transition.
   On failure, the function logs an `ERROR` with the conflict code and
   current status, and the guard `effectiveReviewId !== lastReviewId`
   remains `true` for the next sync cycle to retry.

## Prevention

- Always check return values of CAS-based state transitions
  (`markTaskPlanApproved`, `markTaskPlanChangesRequested`, etc.)
- When a guard condition uses a DB field as a "processed" marker
  (`effectiveReviewId !== lastReviewId`), ensure the marker is set
  only after the state transition succeeds.
- Add a coordinator pipeline stage for `plan_review → implementing`
  as a fallback recovery path.
