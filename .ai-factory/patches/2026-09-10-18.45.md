# Fresh issue planning reused stale deterministic plan files

**Date:** 2026-09-10 18:45
**Files:** packages/agent/src/subagents/planner.ts, packages/agent/src/__tests__/planner.test.ts
**Severity:** high

## Problem

A newly synced GitHub Issue task could still pick up an old plan from a previous run instead of generating a fresh one. In the reported reproduction, the task `#3 Прогон 2` used `.ai-factory/plans/github-issue-3.md`, but that file contained an unrelated older plan (`Implementation Plan: Обогащение кода объяснительными комментариями на русском языке`). The pipeline then advanced through `planning` and `plan_ready`, and the implementer logged `Implementer no-op: all plan tasks already completed`.

## Root Cause

The first stale-plan guard only deleted the target file when `computePlanLayers()` parsed tasks and found all of them completed. That was too narrow for deterministic VCS issue flows:

- GitHub/GitLab issue tasks reuse deterministic branches and plan paths such as `feature/github-issue-3` and `.ai-factory/plans/github-issue-3.md`.
- A worktree for a recreated task can already contain an old plan committed on that deterministic branch.
- The old file might not match the parser's expected `Task N` structure, or it might have partial/inconsistent checkbox state.
- After the planner run, fallback disk reads could also select an old `PLAN.md` if the planner returned inline content and did not touch the fallback file.

The planner therefore treated stale disk artifacts as current task context/output for first-time planning.

## Solution

Changed `runPlanner()` to prepare a clean planning target before fresh non-fix planning. If the task is not a fix, has no `planReviewFeedback`, and has no persisted DB `task.plan`, the planner now deletes the existing target plan file before invoking the runtime. The delete is logged with `[FIX]`; if removal fails, planning blocks manually with a clear error instead of continuing against stale context.

Added a freshness guard to `readPlanFromDisk()`: for first-time planning, fallback files are accepted only if their `mtimeMs` is at or after the current planner run start. This prevents stale root `PLAN.md` or configured fallback paths from overriding fresh inline planner output.

Regression tests cover both stale canonical plan replacement and stale fallback `PLAN.md` rejection, while preserving intentional reuse during replanning or when a persisted DB plan already exists.

## Prevention

- For deterministic branch/path workflows, first-time planning must distinguish pre-existing artifacts from artifacts created during the current run.
- Do not rely solely on plan-content parsing to classify staleness; stale plans may be unparsable or partially checked.
- Add tests for both canonical target plan files and fallback plan files whenever planner output resolution changes.
- During review, verify that fresh planning, replanning, fix planning, and persisted-plan flows each have separate guard conditions.
